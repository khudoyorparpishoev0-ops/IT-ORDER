# ТЗ на редизайн интерфейса HONA ORDER

Техническое задание для дизайнера. Описывает систему целиком: кто ею
пользуется, из каких экранов она состоит, какие данные и действия есть на
каждом, какие правила бренда и техники нельзя нарушать и что именно нужно
получить на выходе. Всё описанное **работает** на `https://order.ithona.tj`:
речь о новом оформлении поверх готовой логики, а не о новом продукте.

Документ самодостаточен. Ссылки на файлы репозитория даны для инженера,
который будет внедрять макеты; дизайнеру достаточно самого текста,
брендбука и скриншотов.

## 1. О продукте

**HONA ORDER** — внутренняя платформа заявок на расходы строительной
компании IT-HONA (Душанбе). Сотрудник просит купить материалы, руководитель
согласует покупку, отдел закупа проверяет склад и называет цены,
руководитель утверждает сумму, бухгалтерия платит. Всё, что происходит с
заявкой, видно её автору и тем, кто её двигает.

| Параметр | Значение |
|---|---|
| Пользователи | 15–20 человек, все — сотрудники компании |
| Язык интерфейса | только русский; эмодзи запрещены |
| Валюта | сомони (TJS); формат `12 500,00` |
| Часовой пояс | Asia/Dushanbe, даты `08.09.2026` |
| Устройства | прорабы, мастера и снабженцы — **с телефона**; руководитель и бухгалтерия — с компьютера |
| Сеть | обычный интернет по HTTPS; внешние CDN не используются, шрифты и библиотеки лежат в сборке |
| Браузеры | актуальные Chrome, Safari (iOS), Firefox, Edge |
| Название | в продукте — **ORDER**; в хендоффе первой версии система называлась CORE, это то же самое |

Мобильная версия — не «на будущее», а основной сценарий для половины
пользователей: подать заявку с объекта, посмотреть, где она застряла,
согласовать в дороге.

## 2. Границы работ и результат

### 2.1. Что меняем

- Внешний вид и раскладку всех экранов панели (перечень в разделе 6) в двух
  ширинах: **390 px** (телефон) и **1440 px** (компьютер).
- Библиотеку компонентов (раздел 7) и дизайн-токены (раздел 8).
- Обе темы: светлая и тёмная.
- Иерархию информации в списках и карточках: что главное, что второстепенное.
- Мобильный сценарий целиком: сегодня это «сжатый десктоп».

### 2.2. Что не меняем

- **Состав данных и логику.** Список полей, набор статусов, права ролей и
  последовательность шагов заданы бизнес-процессом и бэкендом. Дизайнер
  не добавляет поля и не убирает шаги.
- **Набор разделов и адреса.** Новые разделы не придумываем; объединять или
  переименовывать существующие — только через вопрос заказчику
  (раздел 13).
- **Брендбук.** Палитра, логотип, шрифты, радиусы, углы 60°, запрет
  градиентов и «таблеток» — обязательны. Если брендбука не хватает,
  предлагается дополнение к нему отдельным документом, а не обход.
- **Технологический стек.** React + обычный CSS с переменными; UI-киты
  (MUI, Ant, Tailwind) не используются. Макет должен быть реализуем
  этими средствами — на практике это значит: без сложных эффектов
  и без компонентов, которые нельзя описать токенами и разметкой.

### 2.3. Приоритеты экранов

1. **Заявки**: список и карточка заявки — самый частый экран у всех ролей.
2. **Новая заявка** — форма, которую прорабы заполняют с телефона.
3. **Согласование** — двухшаговое решение руководителя.
4. **Панель** — точка входа.
5. **Закуп** — оценка строк и склад.
6. Вход и второй фактор.
7. Отчёты, Команда, Финансы.
8. Сотрудники, Объекты, Журнал, Параметры, Справка — по остаточному принципу,
   но обязательно в рамках той же системы компонентов.

### 2.4. Что должно быть на выходе

**Обязательно**

| # | Результат | Требования |
|---|---|---|
| 1 | Макеты всех экранов раздела 6 в двух ширинах | 390 и 1440 px; Figma (или другой инструмент с экспортом в SVG/PNG и доступом инженера к размерам) |
| 2 | Состояния каждого экрана | загрузка · пусто (с причиной, см. 9.5) · ошибка запроса · «сессия истекла» · много данных (50+ строк) · узкие данные (одна заявка) |
| 3 | Обе темы | светлая и тёмная; допускается светлая полностью + правило вывода тёмной, если правило однозначно |
| 4 | Токены в виде **CSS-переменных** | по образцу `tokens.css` (раздел 8): цвета для двух тем, отступы, радиусы, тени, шрифтовая шкала, плотность |
| 5 | Библиотека компонентов | каждый компонент раздела 7 во всех состояниях: обычное · наведение · нажатие · фокус клавиатурой · отключено · ошибка |
| 6 | Правила сетки и отступов | колонки, поля, межколонник для 390 и 1440; шаг отступов |
| 7 | Мобильные паттерны | шторка меню, карточка заявки на телефоне, полноэкранная форма, лента фильтров, липкие кнопки действий |
| 8 | Иконки | набор линейных иконок (Tabler или совместимый), 24 px, штрих 1.6, список нужных иконок в приложении В |

**Полезно, но не обязательно**

- Прототип кликабельных переходов основного пути: вход → панель → новая
  заявка → отправить → список → карточка.
- Раскладка для промежуточной ширины 768–1024 px (планшет, узкое окно).
- Макеты писем и сообщений Telegram — в системе они есть, но их оформление
  в этот этап не входит.

**Формат передачи.** Ссылка на файл Figma с правами на просмотр и
инспектор + экспорт токенов в текстовый файл `tokens.css`. Шрифты в
макетах — те же, что в продукте: Manrope, JetBrains Mono, Noto Sans.

### 2.5. Этапы и приёмка

| Этап | Содержание | Критерий приёмки |
|---|---|---|
| 1. Концепция | Панель, Заявки (список + карточка), Новая заявка в 390 и 1440, светлая тема | Заказчик подтверждает направление; проверка по чек-листу раздела 12 |
| 2. Основные экраны | Согласование, Закуп, Вход, Отчёты, Финансы, Команда; компоненты; тёмная тема | Все состояния присутствуют; токены выгружены |
| 3. Остальное | Сотрудники, Объекты, Журнал, Параметры, Справка, второй фактор, восстановление пароля | Ни один экран не выпадает из системы компонентов |
| 4. Передача | Финальный файл, токены, замечания инженера отработаны | Инженер может реализовать любой экран без вопросов к дизайнеру |

Чек-лист приёмки каждого макета — раздел 12.

## 3. Роли и права

Пять ролей. Права проверяет сервер на каждом запросе; панель по ним лишь
прячет разделы и кнопки. Интерфейс **не должен предлагать действие,
которого у человека нет** — это не «серая кнопка», а отсутствие кнопки.

| | Сотрудник | Руководитель | Отдел закупа | Финансы | Администратор |
|---|:---:|:---:|:---:|:---:|:---:|
| Подать свою заявку | ✅ | ✅ | ✅ | ✅ | ✅ |
| Видеть чужие заявки | — | ✅ | ✅ | ✅ | ✅ |
| Согласовать покупку и сумму | — | ✅ | — | — | ✅ |
| Проверить склад, поставить цены | — | — | ✅ | — | ✅ |
| Провести выплату | — | — | — | ✅ | ✅ |
| Отчёты, команда, бюджет (видеть) | — | ✅ | — | ✅ | ✅ |
| Задать бюджет месяца | — | — | — | ✅ | ✅ |
| Справочники: сотрудники, объекты, пароли | — | — | — | — | ✅ |
| Журнал действий | — | — | — | — | ✅ |
| Подать заявку за другого | — | — | — | — | ✅ |
| Второй фактор обязателен | — | — | — | ✅ | ✅ |

**Какие разделы видит каждая роль**

| Роль | Разделы в меню |
|---|---|
| Сотрудник | Панель · Заявки · Параметры · Справка |
| Руководитель | + Согласование · Отчёты · Команда · Финансы |
| Отдел закупа | + Закуп |
| Финансы | + Отчёты · Команда · Финансы |
| Администратор | всё: + Сотрудники · Объекты · Журнал |

**Разделение обязанностей** (проверяется на каждом действии, сообщения
показываются как есть):

- Свою заявку нельзя согласовать, оценить или оплатить — даже
  администратору.
- Кто одобрил сумму — тот не платит: «Эту заявку одобрили вы. Выплату
  проводит кто-то другой — так устроено разделение обязанностей.»
- Персональных назначений нет: заявку берёт любой, у кого есть право
  шага. В карточке видно поимённо, кто это может сделать.
- Сотрудник видит только свои заявки. Чужая заявка по ссылке — «не
  найдено», а не «нет доступа».

## 4. Процесс заявки

Главное в системе. Каждый экран так или иначе показывает, **на каком шаге
заявка и кто её держит**.

```
ЧЕРНОВИК ─отправить─▶ СОГЛАСОВАНИЕ ПОКУПКИ ─одобрить─▶ У ЗАКУПА ─оценить─▶ СОГЛАСОВАНИЕ СУММЫ ─утвердить─▶ К ОПЛАТЕ ─оплатить─▶ ОПЛАЧЕНА
                              │                            │                        │
                          отклонить               всё нашлось на складе        отклонить
                              ▼                            ▼                        ▼
                          ОТКЛОНЕНА                 ВЫДАНО СО СКЛАДА            ОТКЛОНЕНА
```

### 4.1. Статусы

Восемь статусов. Статус всегда показывается **цветом и словом**: точка-
индикатор плюс подпись. Одним цветом статус не обозначается.

| Код | Подпись | Индикатор | У кого лежит (подпись в списке) | Полная подпись в карточке | Сумма известна |
|---|---|---|---|---|---|
| `draft` | Черновик | серый | у автора | Черновик у автора | нет |
| `pending` | Согласование покупки | жёлтый | у руководителя | У руководителя: согласовать покупку | нет |
| `sourcing` | У закупа | синий | у закупа | У отдела закупа: склад и цены | нет |
| `priced` | Согласование суммы | жёлтый | у руководителя | У руководителя: утвердить сумму | да |
| `approved` | К оплате | синий | в бухгалтерии | В бухгалтерии: ждёт выплаты | да |
| `paid` | Оплачена | зелёный | — (закрыта) | Выплачена | да |
| `fulfilled` | Выдано со склада | зелёный | — (закрыта) | Закрыта складом | нет, денег не было |
| `rejected` | Отклонена | красный | — (закрыта) | Отклонена | если отклонена после оценки |

Порядок статусов в фильтрах: Согласование покупки · У закупа · Согласование
суммы · К оплате · Оплачена · Выдано со склада · Отклонена · Черновик.

Смысл цветов: **жёлтый** — ждёт решения человека, **синий** — в работе у
службы, **зелёный** — завершена благополучно, **красный** — отклонена,
**серый** — ещё не подана.

### 4.2. Шаги и кто их делает

| Шаг | Кто | Что вводит | Что видит после |
|---|---|---|---|
| Создать / сохранить черновиком | автор (администратор — за любого) | объект, строки «что нужно · сколько · единица». **Цен нет намеренно** | заявка в списке со статусом Черновик; её можно править и удалить |
| Отправить на согласование | автор | — | статус «Согласование покупки», руководителям уходит письмо и Telegram |
| Согласовать покупку / отклонить | руководитель | комментарий: необязателен при одобрении, **обязателен при отклонении** | «У закупа» или «Отклонена» |
| Оценить | отдел закупа | по каждой строке **либо** цена за единицу, **либо** отметка «есть на складе»; пояснение необязательно | если всё со склада — «Выдано со склада», иначе «Согласование суммы» с итогом |
| Утвердить сумму / отклонить | руководитель (может быть другой человек) | комментарий, при отклонении обязателен | «К оплате» или «Отклонена» |
| Провести выплату | финансы, не тот, кто утвердил | способ (На карту / Наличными), номер документа, дата (не из будущего, не раньше решения) | «Оплачена» |

### 4.3. Правила, которые интерфейс обязан отражать

1. **До оценки закупа у заявки нет суммы.** В списке и карточке стоит
   «не оценена», не «0,00». Признак `priced` в данных отвечает именно на
   этот вопрос.
2. **Складская строка денег не стоит.** У неё нет цены и суммы, в итог она
   не входит, в списке такая заявка показывает «со склада».
3. **«У кого сейчас и сколько дней»** — самый частый вопрос. Считается от
   момента входа в текущий шаг, а не от подачи. У закрытых заявок дней нет.
4. **Заявка неизменяема после подачи.** Править состав можно только у
   черновика. Ошибка исправляется новой заявкой. Кнопок «изменить» у
   поданной заявки быть не должно.
5. **История событий** — линейная лента: создана → отправлена → одобрена /
   со склада / оценена → утверждена → выплачена / отклонена. Каждая запись:
   текст, кто, когда (`ИВАН ПЕТРОВ · 04.09.2026, 18:12`).
6. **Лимит сотрудника** показывается, но не блокирует: в карточке
   согласования видно «лимит» и «израсходовано за месяц», решение — за
   руководителем.
7. **Номер заявки** — `РЗ-0001`, пропуски в нумерации допустимы.
8. Заявки, стоящие на одном шаге дольше 3 дней, получают напоминание
   (письмо + Telegram) тому, у кого они лежат. В интерфейсе просится
   выделение таких заявок.

## 5. Каркас панели (шелл) и навигация

### 5.1. Как устроено сейчас

- **Сайдбар 240 px** слева, на всю высоту. Сверху горизонтальный логотип
  и подпись `ORDER` (моно). Далее список разделов: иконка 20 px + подпись
  15 px, высота пункта 44 px. Активный пункт — плашка, не подчёркивание.
- **Низ сайдбара:** кнопка-ссылка «ДИЗАЙН-СИСТЕМА» (внутренний эталон,
  в новом дизайне можно убрать в «Параметры» или оставить), переключатель
  темы (иконка солнце/луна), квадратный аватар 36 px с инициалами, имя и
  роль, кнопка «Выйти», версия сборки `v1.0 · 09-08`.
- **Контент** до 1240 px шириной, поля 32 px (16 px на телефоне).
- **Два варианта панели** переключаются в «Параметрах»:

| Вариант | Сайдбар | Плотность | Панель |
|---|---|---|---|
| B «Диспетчер» (по умолчанию) | тёмно-зелёный `forest`, белый текст | compact | таблица заявок первым блоком |
| C «Светлый» | белый `paper` с обводкой `line`, зелёный только в акцентах | mid | сначала показатели, потом таблица |

Оба варианта — одна кодовая база: меняются только тема, плотность и цвет
сайдбара. **Решение по вариантам открыто** (раздел 13): дизайнер может
предложить оставить один, но тогда нужно обосновать.

- **Телефон (≤ 900 px):** сайдбар уходит в шторку `min(86vw, 320px)` со
  скримом; сверху липкая полоса с кнопкой меню 48×48 и горизонтальным логотипом.
  Клик по разделу закрывает шторку.

### 5.2. Порядок разделов (фиксирован)

Панель · Заявки · Согласование · Закуп · Отчёты · Команда · Финансы ·
Сотрудники · Объекты · Журнал · Параметры · Справка.

Разделы без права не показываются вовсе. Переход по адресу закрытого
раздела молча возвращает на панель.

### 5.3. Глобальные состояния приложения

| Состояние | Что показывается |
|---|---|
| Первичная загрузка | пустой экран с подписью `ЗАГРУЗКА` |
| Сервер недоступен | карточка «Сервер не отвечает» + текст ошибки + «Проверьте подключение и повторите. Если не проходит — сообщите администратору системы.» + кнопка «Повторить» |
| Нет сессии | экран входа вместо панели |
| Сессия истекла в работе | экран входа с плашкой: «Сессия истекла — войдите заново. Если вы что-то заполняли, эти данные не сохранились: их придётся ввести ещё раз.» |
| Тост | вверху справа, 3,2 с, левая кромка и квадрат-индикатор цвета события; тексты вида «Заявка РЗ-0012 отправлена на согласование» |

Задача дизайнеру: эти состояния сейчас минимальны — нужны полноценные
макеты каждого.

## 6. Экраны

Для каждого экрана: кто видит, что на нём есть, какие действия, какие
состояния, что болит и что ждём от дизайнера. Тексты подписей и кнопок
приведены как есть — их можно улучшать, но смысл менять нельзя.

### 6.1. Вход `/login`

**Кто:** все, без сессии. Композиция по центру, ширина 400 px, вертикальный
логотип и подпись `ORDER` сверху.

**Шаг 1 — почта и пароль.** Заголовок «Вход в систему», подпись «Заявки на
расходы сотрудников». Поля «Корпоративная почта» (подсказка
`name@ithona.tj`) и «Пароль». Кнопка «Войти» на всю ширину. Кнопка
«Забыли пароль?» (только если на сервере настроена почта). Подпись «Вход
только с корпоративной почты (@ithona.tj)». Ошибка под полями:
«Неверная почта или пароль» / «Слишком много неудачных попыток. Вход
заблокирован примерно на 15 мин.» / «Учётная запись отключена. Обратитесь
к администратору.»

**Шаг 2 — код подтверждения** (у кого включён второй фактор). Заголовок
«Код подтверждения», подпись «Откройте приложение-аутентификатор и введите
шестизначный код», поле «Код из приложения» (6 цифр, моно, широкий
трекинг), кнопки «Подтвердить» и «Войти под другой учётной записью».
Подпись: «Потеряли телефон — введите один из кодов восстановления. Если их
тоже нет, второй фактор сбросит администратор.»

**Шаг 2а — обязательная настройка второго фактора** (финансы и
администратор при первом входе). Карточка 520 px: «Требуется
двухфакторный вход», пояснение, три шага (установите приложение →
отсканируйте QR 180×180 или введите ключ вручную → введите код), кнопка
«Включить», затем экран **кодов восстановления**: список из кодов (моно,
сетка), «Копировать», чекбокс «Я сохранил коды», «Продолжить» (неактивна,
пока не отмечен чекбокс). Коды показываются один раз — экран нельзя
пропустить случайно.

**Восстановление пароля** `/reset-password`: запрос ссылки (поле почты,
«Прислать ссылку», «Вернуться ко входу») → «Проверьте почту» → по ссылке
из письма: «Новый пароль» + «Повторите пароль» → «Пароль изменён» →
«Перейти ко входу».

**Ждём от дизайнера:** экран входа на телефоне (клавиатура закрывает
половину экрана — форма должна оставаться видимой), сцену ввода кода,
экран кодов восстановления, который невозможно закрыть по ошибке.

### 6.2. Панель `/`

**Кто:** все. Содержимое зависит от роли.

**Шапка:** рубрика `РАСХОДЫ · СЕНТЯБРЬ 2026`, заголовок «Панель
управления», подзаголовок: для руководителя «Команда из 8 сотрудников,
10 заявок за период», для сотрудника — его имя и должность. Кнопки
«Экспорт» (Excel по текущему периоду) и «Новая заявка».

**Блоки:**

1. **Показатели за месяц** (только у кого есть отчёты): «ВСЕГО ЗАЯВОК»
   (число, «за сентябрь, 8 сотрудников»), «ОДОБРЕНО, TJS» (сумма, «1
   заявка, ждут выплаты»), «НА УТВЕРЖДЕНИИ, TJS» (сумма только по
   оценённым, «4 заявки ждут решения»), «БЮДЖЕТ МЕСЯЦА, TJS» (сумма,
   «использовано 5 %» или «бюджет не задан»).
2. **Баннер очереди** (только руководителю, если очередь не пуста):
   «2 заявки ждут вашего решения», «Самая давняя заявка: Иван Петров,
   сегодня. Ещё 2 заявки вернулись из закупа и ждут решения по сумме.»,
   кнопка «Перейти к согласованию». Сейчас — тёмно-зелёная плашка со
   срезом угла 60°.
3. **Заявки за месяц:** заголовок, поиск по сотруднику, кнопка «Все
   заявки», список заявок (компонент 7.9). Сотрудник видит только свои.

Порядок блоков зависит от варианта панели (5.1).

**Состояния:** нет заявок за период («Заявок за период пока нет. Как
только сотрудники подадут заявки, они появятся здесь.»), поиск ничего не
нашёл («По запросу заявок нет» + «Очистить поиск»), ошибка загрузки.

**Что болит:** таблица занимает половину ширины карточки (см. скриншот
`desk-light-B-dashboard.png`); у сотрудника панель почти пуста — нет
показателей, нет баннера, только список своих заявок; не видно «что от
меня требуется сейчас».

**Ждём от дизайнера:** панель для трёх ситуаций — сотрудник (мои заявки и
где они), руководитель (очередь решений и бюджет), бухгалтерия (к оплате).
Возможна одна раскладка с блоками по роли.

### 6.3. Заявки `/requests`

**Кто:** все; сотрудник — только свои.

**Шапка:** рубрика периода, «Заявки», «10 заявок за сентябрь», кнопки
«Excel» и «Новая заявка».

**Фильтры:** чипы «Все» + восемь статусов (4.1); справа выбор периода
«Текущий месяц» / «Все периоды». Статус пишется в адрес (`?status=approved`
— так с «Финансов» ведёт ссылка к одобренным).

**Список** (компонент 7.9): по 20 на страницу, сортировка по сотруднику и
сумме, пагинация «ПОКАЗАНО 10 ИЗ 10» + стрелки + номера страниц.

**Строка списка содержит:** имя · должность · объект · номер · дата · сумма
(или «не оценена» / «со склада») · статус (цвет + слово) · у кого лежит и
сколько дней · ссылка «Открыть →» (руководителю на ожидающих —
«Рассмотреть →»).

**Состояния:** пусто по фильтру («По выбранному фильтру заявок нет» +
«Сбросить фильтр»), загрузка, ошибка.

**Телефон:** чипы — лента с горизонтальной прокруткой, список — карточки,
сортировки нет.

**Что болит:** семь смысловых единиц в строке без иерархии; восемь чипов
занимают две строки и плохо читаются; на телефоне карточка занимает 160 px
на одну заявку; нет быстрого ответа «где мои заявки застряли».

**Ждём от дизайнера:** иерархия строки (главное — кто/что/статус/у кого,
второстепенное — номер, дата, должность), компактный фильтр по статусам
(группировка: «ждут меня», «в работе», «закрыты» — обсуждаемо),
мобильная карточка заявки высотой не более 100 px, выделение
залежавшихся (3+ дня).

### 6.4. Карточка заявки (модальное окно)

Открывается из любого списка. Ширина 600 px, высота до 82 % экрана.

**Содержимое сверху вниз:**

1. `РЗ-0001 · 08.09.2026`, имя автора, крестик.
2. Три поля: ОБЪЕКТ, СУММА TJS («ещё не оценена» / сумма / «выдано со
   склада»), СТАТУС (плашка).
3. Таблица состава: ОПИСАНИЕ · КОЛ-ВО (`2 канистра`) · СУММА TJS
   («не оценено» / «со склада» / число).
4. Блок «СЕЙЧАС ЖДЁТ»: «У руководителя: согласовать покупку · 2 дня»,
   ниже имена тех, кто может двинуть заявку. У закрытых блока нет.
5. Комментарий закупа («Закуп (Ольга Кузнецова): …») и комментарий
   решения — абзацы с левой чертой.
6. **Форма выплаты** (только финансам и только у статуса «К оплате»):
   способ («Перевод на карту» / «Наличные»), «Документ» (подсказка
   `ПП-0412`), кнопка «Провести выплату». После выплаты: «Выплачено
   1 485,00 TJS, документ ПП-0409.»
7. Кнопки: «Открыть в согласовании» (руководителю у ожидающих), «PDF»,
   «Закрыть».

**Чего в карточке нет, но должно быть по смыслу:** лента шагов процесса
(где заявка на пути из шести шагов), история событий (сейчас она есть
только в «Согласовании»), кнопки автора для черновика («Отправить»,
«Удалить»; править черновик сейчас можно только через API — это известный
пробел).

**Ждём от дизайнера:** на телефоне карточка — полноэкранный лист с липкой
шапкой и кнопками внизу; на компьютере — модальное окно или боковая
панель (решает дизайнер). Обязательна лента шагов.

### 6.5. Новая заявка (модальное окно)

**Кто:** все. Открывается с Панели и из Заявок.

**Форма:** заголовок «Что нужно купить». Поле «Сотрудник» (только
администратору — выбор за кого; остальным — просто имя). Поле «Объект»
(выпадающий список активных объектов; пустой список объясняется
причиной — см. 9.5). Блок «СОСТАВ РАСХОДОВ»: строки «Что нужно» (с
подсказками из прошлых заявок: «мешок · заказывали 3 раза») · «Кол-во» ·
«Единица» (`шт.`), кнопка удаления строки, «Ещё строка». Пояснение: «Цены
указывать не нужно: заявку сперва согласует руководитель, потом отдел
закупа проверит склад и проставит стоимость того, чего нет.» Кнопки:
«Отправить на согласование» (главная), «Сохранить черновиком», «Отмена».
Подпись: «Черновик виден только вам и в согласование не попадает.
Отправленную заявку править уже нельзя.»

**Поведение:** закрытие с заполненной формой спрашивает: «Закрыть без
сохранения? Введённое не сохранится.» — «Закрыть без сохранения» /
«Вернуться к форме». Ошибки: «Выберите сотрудника и объект», «Добавьте
хотя бы одну строку: что нужно купить».

**Что болит:** на телефоне кнопка «Сохранить черновиком» и подпись под ней спрятаны за прокруткой внутри окна и не видны сразу
(`mob-light-B-new-request-modal.png`); строки сметы в столбик читаются
плохо; подсказка материалов — стандартный `datalist` браузера.

**Ждём от дизайнера:** полноэкранная мобильная форма с крупными полями,
строка сметы как карточка, свой список подсказок, липкая панель с двумя
кнопками. Это экран, который прораб заполняет на стройке в перчатках.

### 6.6. Согласование `/approvals`

**Кто:** руководитель, администратор.

**Шапка:** «Согласование», подпись «Сперва согласуйте саму покупку, после
оценки закупа — сумму. Комментарий к отклонению обязателен».

**Вкладки-чипы:** «Покупка · 2» (ждут согласования покупки), «Сумма»
(вернулись из закупа с ценами), «У закупа», «К оплате», «Отклонены».

**Три колонки:**

1. **Очередь:** `ОЧЕРЕДЬ · 2`, пункты: имя, сумма (сейчас у неоценённых
   показывается «0,00» — дефект), номер · дата, объект. Первая выбрана
   автоматически. «Показать ещё» при длинной очереди.
2. **Карточка:** аватар-инициалы 44 px, имя, «Дизайнер · объект «Офис на 7
   этаже»», почта · телефон, плашка статуса, номер и дата. Таблица:
   ОПИСАНИЕ · КОЛ-ВО · ЦЕНА TJS · СУММА TJS, итог «Итого к оплате» или
   «Сумму назовёт закуп». Три показателя: ЛИМИТ СОТРУДНИКА, ИЗРАСХОДОВАНО,
   ПОЗИЦИЙ В ЗАЯВКЕ. Ниже — «История изменений»: события с левой чертой,
   последнее — зелёной.
3. **Решение** (липкая колонка): два квадратных радио «Согласовать
   покупку» / «Утвердить сумму» (зелёный акцент) и «Отклонить» (красный);
   поле «КОММЕНТАРИЙ» (подсказка при отклонении: «Укажите причину
   отклонения: факт, причина, что делаем, срок»); главная кнопка меняет
   цвет и текст: «Согласовать покупку» / «Утвердить 3 100,00 сомони» /
   «Отклонить заявку»; «Отмена». Если заявка своя — вместо формы карточка
   «ВАША ЗАЯВКА: Собственную заявку согласовать нельзя. Решение примет
   другой руководитель.» У закрытых — «РЕШЕНИЕ ПРИНЯТО»: статус, кто,
   комментарий, выплата.

**Состояния:** «Все заявки рассмотрены» / «Оценённых заявок нет» / «В этой
вкладке заявок нет».

**Что болит:** на телефоне три колонки складываются в столбик, и форма
решения оказывается в самом низу после долгой прокрутки
(`mob-light-B-approvals.png`); во вкладке «Сумма» справа появляются сразу
два блока («РЕШЕНИЕ» и «РЕШЕНИЕ ПРИНЯТО»).

**Ждём от дизайнера:** мобильный сценарий «список → карточка → решение»
экранами, а не колонками; на компьютере — очередь и карточка с липкой
панелью решения; понятное различие двух шагов (покупка vs сумма).

### 6.7. Закуп `/sourcing`

**Кто:** отдел закупа, администратор.

**Шапка:** рубрика «ЗАКУПКИ», «Оценка заявок», подпись «Проверьте склад и
проставьте цены на то, чего нет. Сумму утверждает руководитель».

**Две колонки:** очередь `ЖДУТ ОЦЕНКИ · 1` (имя, объект · номер · дата) и
карточка оценки: номер · дата, имя, должность · объект, плашка «У закупа»;
таблица ЧТО НУЖНО · КОЛ-ВО · ЦЕНА ЗА ЕДИНИЦУ (поле ввода `0,00`) · ЕСТЬ НА
СКЛАДЕ (квадратный чекбокс «Покупаем» → «Со склада»; отметка стирает
цену); итог «К ПОКУПКЕ · 1 со склада — 1 240,00 TJS» или «ВСЁ СО СКЛАДА»;
поле «Пояснение» («срок действия цены, поставщик, что нашлось на
складе»); кнопка «Отправить руководителю» либо «Закрыть складом»; подпись
«Руководитель увидит сумму и 2 строки с ценами.» Свою заявку оценить
нельзя — кнопка заблокирована с пояснением.

**Ошибка:** «Строка «Крепёж»: укажите цену или отметьте, что есть на
складе».

**Ждём от дизайнера:** мобильная форма ввода цен (снабженец ходит по
складу с телефоном): строка = карточка с крупным полем цены и большим
переключателем «со склада», итог всегда виден.

### 6.8. Отчёты `/reports`

**Кто:** руководитель, финансы, администратор.

**Заголовок — вывод, а не рубрика:** «Больше всего расходов за сентябрь —
объект «Речь»», подпись «Источник: ORDER · данные на 08.09.2026». Кнопки
«Excel» и «PDF» (реестр выплат).

**Два графика:** «ДОЛИ ПО ОБЪЕКТАМ, TJS» — горизонтальные полосы с
суммой и процентом; «ФАКТ ПО МЕСЯЦАМ, TJS ТЫС.» — столбики за 6 месяцев,
текущий — зелёный, ось от нуля, значения над столбцами. Круговых диаграмм
не использовать.

**История оплаченных заявок:** подпись «1 выплата с 08.09.2026 по
08.09.2026 · средний срок от одобрения до выплаты 0 дней», фильтр по
объекту, кнопка «Реестр выплат», таблица ОПЛАЧЕНА · СОТРУДНИК · ОБЪЕКТ ·
СУММА TJS · ВЫПЛАТА (способ + документ), итог «Итого выплачено за
сентябрь».

**Состояния:** «Расходов за период нет», «Выплат за период не было».

### 6.9. Команда `/team`

**Кто:** руководитель, финансы, администратор. Таблица: СОТРУДНИК
(имя + должность) · ЛИМИТ TJS · ИЗРАСХОДОВАНО (полоса + «1 240,00 · 31 %»;
цвет полосы: зелёный, от 90 % жёлтый, от 95 % красный) · ЗАЯВОК. Пусто:
«Сотрудники не заведены» + «Добавить сотрудника» (администратору).

### 6.10. Финансы `/finance`

**Кто:** руководитель, финансы, администратор.

Две карточки: «БЮДЖЕТ НА МЕСЯЦ, TJS» (крупная сумма, полоса, «Использовано
7 865,00 · осталось 148 135,00» или «Бюджет на месяц не задан»; кнопка
«Задать бюджет» / «Изменить бюджет» — только финансам, раскрывает поле и
«Сохранить» / «Отмена») и «К ВЫПЛАТЕ, TJS» (сумма, «1 одобренная заявка
ждёт перечисления», кнопка «Перейти к одобренным»). Ниже заглушка:
«ЧЕРНОВИК · В РАБОТЕ — Банковские реквизиты не подключены».

### 6.11. Сотрудники `/employees`

**Кто:** администратор.

Поиск «Имя, должность или почта», чип «Показать отключённых (2)», кнопка
«Добавить сотрудника». Таблица: СОТРУДНИК · ПОЧТА · РОЛЬ («это вы») ·
ЛИМИТ TJS · ДОСТУП (точка + слово: «Вход открыт» / «Пароль не задан» /
«Без почты» / «Заблокирован» / «Отключён») · ВТОРОЙ ФАКТОР («Включён ·
кодов: 8» / «Настроит при входе» / «Выключен»).

**Карточка сотрудника (модальное окно):** «Имя и фамилия», «Должность»,
«Рабочая почта» (она же логин), «Телефон», «Роль» (с пояснением роли),
«Месячный лимит, TJS», чекбокс «Работает в компании», у новой записи —
«Пароль для входа» с кнопкой «Сгенерировать» (пароль показывается один
раз). Блок «ДОСТУП В СИСТЕМУ»: последний вход, второй фактор, поле
«Новый пароль» + «Заменить пароль», «Сбросить второй фактор» (с

### 8.3. Форма и размеры

- Радиусы: **0** — плашки, шапки таблиц, теги; **2** — поля, чипы,
  аватар, пункты меню; **4** — кнопки, карточки, окна. Других нет.
- Обводки: 1 px `line` (карточки, разделители), 1 px `grey` (поля,
  вторичные кнопки), 2 px `green` (активное, фокус).
- Тени: только `sh1 = 0 1px 2px rgba(16,22,19,.06)` и `sh2 = 0 8px 24px
  rgba(16,22,19,.14)`; sh2 — только у оверлеев. Третьего уровня нет.
- Углы-акценты только 60° (30° как дополнение), 45° не используется. Срез
  угла — один на экран. Штриховка 60° для пустых состояний и «в работе».
- Шаг отступов: 4 · 8 · 12 · 16 · 24 · 32 · 48 · 64.
- Контент до 1240 px, поля 32 / 16 px, межколонник 24 px, сайдбар 240 px.
- Кнопка 44 (48 на телефоне), строка таблицы 44, пункт меню 44.
- Плотность (переключается с вариантом): compact `--pad 16 / --gap 12 /
  ячейка 8×12`, mid `20 / 16 / 10×14`, airy `24 / 24 / 12×16`.
- Движение: одна анимация **150 ms ease-out**. Параллакс, появление по
  скроллу, переходы между экранами, градиенты — запрещены.

### 8.4. Иконки

Линейные, из набора **Tabler Icons** (MIT), 24 px при штрихе 1,6,
`stroke-linecap: butt`, `stroke-linejoin: miter`, цвет через
`currentColor`. Размеры в интерфейсе: 14 / 18 / 20 / 24. Цветные иконки и
эмодзи запрещены. Список используемых — приложение В. Новые иконки — из
того же набора.

### 8.5. Логотип

Только готовые композиции: вертикальная (основная — вход, восстановление
пароля), горизонтальная (сайдбар, верхняя полоса на телефоне), знак без
слова (favicon, места ≤ 24 px). Цвет один: зелёный на светлом, белый на
тёмном и на зелёном. Имя нельзя набирать шрифтом — начертание фирменное.
Охранное поле — толщина штриха знака; минимальные размеры: горизонтальная
96 px, вертикальная 72 px, знак 24 px. Файлы — `docs/brand/`.

### 8.6. Графики

Один график — один вывод, он же заголовок. Данные без источника и даты не
публикуются. Круговые диаграммы не использовать, ось от нуля обязательна,
подписи значений рядом с элементами, сетка минимальная, текущий период —
акцентный цвет.

## 9. Правила контента

### 9.1. Язык

Русский, без эмодзи. Падежи: после «за» — винительный («за сентябрь»).
Имена людей в предлоги не ставить — давать через двоеточие («Самая давняя
заявка: Иван Петров»). Числительные склоняются: «1 заявка», «2 заявки»,
«5 заявок»; «1 день», «3 дня», «5 дней».

### 9.2. Числа и деньги

`1 250 000,00` — разряды через пробел, копейки через запятую, всегда два
знака. Валюта в заголовке колонки (`СУММА, TJS`) или словом «сомони»
после числа. Знак валюты в число не ставится. Отсутствие значения — «—».
Суммы в моно.

### 9.3. Даты

`08.09.2026`, дата-время `08.09.2026, 18:12`, часовой пояс компании.
Относительное время только в подписях: «сегодня», «3 дня назад», «· 2
дня» у заявки на шаге.

### 9.4. Статусы и шаги

Только подписи из 4.1. Сокращать нельзя. «У кого лежит» — подписи из
той же таблицы.

### 9.5. Пустые состояния — с причиной

Одна фраза на все случаи запрещена: «не загрузилось», «всё отключено» и
«ничего не заведено» лечатся по-разному. Примеры действующих текстов:
«Объектов нет. Заведите их в разделе «Объекты» — без объекта заявку не
подать.» / «Все объекты отключены. Включить нужный можно в разделе
«Объекты» — это делает администратор.» / «Не удалось загрузить объекты:
… Обновите страницу.»

### 9.6. Ошибки и подтверждения

Ошибка сервера показывается текстом как есть — они написаны для людей
(«Нельзя согласовать собственную заявку»). Подтверждения опасных действий
— внутри интерфейса, не системным диалогом браузера: вопрос + «Да» /
«Отмена» рядом с кнопкой.

## 10. Доступность и мобильные требования

1. Всё достижимо клавишей Tab в логичном порядке; фокус видим: 2 px
   зелёная обводка с отступом 2 px, без смещения элемента.
2. Esc закрывает окно; Enter/Пробел активируют кнопки и строки списка.
3. Контраст текста не ниже AA (4,5:1), у крупных заголовков — 3:1. Обе
   темы проверяются отдельно.
4. Статус, доступ, состояние — всегда цвет **и** слово или иконка.
5. Подпись поля связана с полем (для диктора и автотестов).
6. Зоны нажатия на телефоне не меньше 44×44 px, кнопки 48 px.
7. Ничего не прокручивается вбок, кроме таблиц внутри своего контейнера и
   ленты чипов. Автотест `npm run mobile` падает при горизонтальной
   прокрутке страницы, шторки или окна.
8. Главное действие экрана на телефоне доступно без прокрутки (липкая
   панель внизу допустима).
9. Формы работают при открытой клавиатуре: поле ввода не должно уходить
   под неё.
10. Тёмная тема — не инверсия, а своя палитра (8.1).

## 11. Техническая сторона внедрения

Чтобы макет было чем реализовать, дизайнеру полезно знать:

- **Стек:** React 18 + TypeScript + Vite. Стили — обычный CSS с
  переменными и классами; Tailwind, styled-components и UI-киты не
  используются и вводиться не будут.
- **Структура:** `frontend/src/pages` — экраны (по одному файлу на
  раздел), `components` — общие блоки (раздел 7), `shell` — сайдбар и
  каркас, `styles` — токены и базовые классы, `api` — типы и запросы,
  `data` — подписи статусов, форматирование чисел и дат.
- **Данные приходят готовыми к показу:** суммы строками (`"1240.00"`),
  даты уже в поясе компании, подписи статусов и «у кого лежит» — на
  стороне панели. Дизайнеру не нужно придумывать вычисления: всё, что
  перечислено в разделах 4 и 6, у экрана уже есть; чего нет в перечне —
  нет и в данных (например, фотографий, аватаров, категорий расходов).
- **Шрифты самохостятся** из npm-пакетов подмножествами latin, latin-ext,
  cyrillic, cyrillic-ext. Внешних загрузок нет: панель должна открываться
  при плохом интернете.
- **Проверки перед выпуском:** сборка, дымовой прогон всех разделов под
  каждой ролью в обеих темах и обоих вариантах (ошибки консоли, ответы
  4xx/5xx), прогон на телефоне 390 px.
- **Объём:** 16 экранов, ~21 общий компонент, 2 темы, 2 варианта
  плотности. Внедрение по экранам, без остановки продукта: токены →
  компоненты → экраны по приоритету 2.3.
- **Что упрощает внедрение:** имена переменных как в `tokens.css`; размеры
  из шага 4 px; один компонент — одно поведение во всех экранах; состояния
  в макете подписаны (hover, focus, disabled, error, loading, empty).

## 12. Чек-лист приёмки макета

Макет экрана принимается, если по каждому пункту «да»:

- [ ] Есть версии 390 px и 1440 px.
- [ ] Есть состояния: загрузка, пусто (с причиной), ошибка, много данных.
- [ ] Есть светлая и тёмная тема (или однозначное правило вывода).
- [ ] Все цвета — из токенов 8.1; новых цветов нет.
- [ ] Радиусы только 0 / 2 / 4; тени только у оверлеев; градиентов нет.
- [ ] Статус — цвет и слово; круглых аватаров и «таблеток» нет.
- [ ] Логотип — готовая композиция, не набранный текст.
- [ ] Шрифты Manrope / JetBrains Mono / Noto Sans; курсива нет.
- [ ] Суммы `1 250,00`, валюта в заголовке или словом; даты `08.09.2026`.
- [ ] Русские тексты со склонением числительных; эмодзи нет.
- [ ] Главное действие на телефоне доступно без прокрутки.
- [ ] Зоны нажатия ≥ 44 px; фокус виден.
- [ ] Нет данных и действий, которых нет в разделах 4 и 6.
- [ ] Компонент повторяет библиотеку раздела 7, а не нарисован заново.
- [ ] У графика есть вывод-заголовок, источник и дата; ось от нуля.

## 13. Известные дефекты и открытые вопросы

### 13.1. Дефекты текущего интерфейса (видны на скриншотах)

Исправлено в коде после съёмки скриншотов, макет должен учитывать
исправленное состояние:

- Согласование: в очереди у неоценённых заявок показывалось «0,00» —
  теперь «не оценена», у закрытых складом «со склада».
- Согласование, вкладка «Сумма»: справа были сразу два блока — остался
  один, форма решения.
- Черновик: в карточке появились «Отправить на согласование», «Изменить»
  (та же форма, что при подаче) и «Удалить» с подтверждением.
- Журнал: действия закупа («Покупка согласована, передана в закуп»,
  «Оценена закупом», «Закрыта складом») получили подписи.
- Справка: семь ответов переписаны под нынешний путь заявки.

Остаётся дизайнеру:

1. Панель: таблица занимает половину ширины карточки
   (`desk-light-B-dashboard.png`).
2. Новая заявка на телефоне: кнопка «Сохранить черновиком» видна только
   после прокрутки внутри окна (`mob-light-B-new-request-modal.png`).
3. Согласование на телефоне: форма решения в самом низу после трёх
   экранов прокрутки.
4. Журнал, Сотрудники, Команда, Реестр выплат на телефоне — таблицы с
   горизонтальной прокруткой шириной 540–860 px.
5. Панель сотрудника почти пуста.

### 13.2. Вопросы, которые решает заказчик

1. **Оставлять ли два варианта панели** (B «Диспетчер» и C «Светлый»)
   или свести к одному с настройкой плотности?
2. **Карточка заявки на компьютере:** модальное окно, боковая панель или
   отдельная страница с адресом (последнее удобно для ссылок из писем и
   Telegram)?
3. **Группировка фильтров статусов:** оставить восемь чипов или ввести
   группы «ждут меня» / «в работе» / «закрыты» с раскрытием?
4. **Таджикский язык:** брендбук требует его для клиентских носителей; для
   внутренней панели переключатель не планировался. Подтвердить.
5. **Раздел «Дизайн-система»** в сайдбаре: оставить как внутренний
   инструмент или убрать из продукта?
6. **Банковские реквизиты в «Финансах»** — заглушка; будет ли этот блок
   вообще?
7. **Фотографии объектов:** данных нет; если появятся — по правилам
   раздела 04 брендбука (реальные объекты, без скруглений и рамок).

## Приложение А. Что доступно экрану из данных

Сокращённая карта, чтобы дизайнер не рисовал того, чего нет.

| Экран | Данные |
|---|---|
| Список заявок | номер, дата, автор (имя, должность), объект, сумма + признак «оценена», статус, у кого лежит + дней на шаге |
| Карточка заявки | + почта и телефон автора, лимит и расход автора за месяц, строки (описание, кол-во, единица, цена, сумма, «со склада»), события (текст, кто, когда), выплата (сумма, способ, документ, дата), комментарии закупа и решения, кто решил, кто оценил, поимённо «кто может двинуть» |
| Панель, показатели | всего заявок, сотрудников подало, одобрено (сумма, кол-во), на утверждении (сумма по оценённым, кол-во), бюджет, % использования; очередь: сколько ждёт, самая давняя (имя, дней), сколько с ценами |
| Отчёты | доли по объектам (название, сумма, %), факт по месяцам (6–24 мес., тыс. TJS), реестр выплат (дата, номер, сотрудник, объект, сумма, способ, документ), сводная фраза, итог |
| Финансы | лимит месяца, использовано, остаток, %, к выплате (сумма, кол-во) |
| Команда | имя, должность, лимит, расход, %, число заявок |
| Сотрудники | карточка + доступ: может входить, есть пароль, второй фактор (вкл./обязателен), кодов осталось, последний вход, блокировка до |
| Объекты | название, активен, число заявок, расход |
| Журнал | время, раздел, запись, действие, кто, адрес, подробности |
| Параметры | профиль, права, последний вход, второй фактор, коды, три переключателя уведомлений, настроена ли почта, Telegram (настроен бот, привязан, @username), последние запуски задач |
| Материалы (подсказки) | название, единица, сколько раз заказывали |

Чего нет: аватаров и фото, категорий расходов, приоритетов, сроков,
вложений, комментариев-переписки, назначения конкретного согласующего,
истории правок (заявка неизменяема).

## Приложение Г. Словарь

| Термин | Значение |
|---|---|
| Заявка | документ «что нужно купить» от сотрудника; после подачи неизменяема |
| Строка / позиция | одна вещь в заявке: название, количество, единица; после закупа — цена и сумма или отметка «со склада» |
| Объект | стройка или площадка, на которую списывается расход |
| Лимит | месячный лимит расходов сотрудника; показывается, не блокирует |
| Бюджет месяца | сумма, которую задаёт бухгалтерия; от неё считаются проценты |
| Закуп | отдел закупа и его шаг: проверить склад, поставить цены |
| Держатель / «у кого лежит» | роль, которая должна сделать следующий шаг |
| Второй фактор | код из приложения-аутентификатора при входе |
| Коды восстановления | одноразовые коды на случай потери телефона |
| Журнал | неизменяемый лог действий пользователей |
