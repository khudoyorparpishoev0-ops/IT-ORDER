# HONA ORDER — платформа заявок на расходы

Внутренний продукт IT-HONA (Душанбе). Сотрудник подаёт заявку на расход,
руководитель согласует, финансы выплачивают. Суммы в сомони (TJS),
интерфейс русский, светлая и тёмная темы.

Дизайн зафиксирован хендоффом UI-кита, вторая редакция от 09.09.2026:
`docs/design/README.md` (рядом — кликабельные прототипы и скриншоты
экранов в `docs/screens/design/`; во второй редакции дашборд стал
рабочей очередью, а на телефоне добавилась нижняя панель навигации),
брендбук IT-HONA rev. 1.0 — `docs/Brand_Book_IT-HONA.pdf`. Брендбук
приоритетнее всего остального. Первый хендофф `docs/DESIGN_HANDOFF.md`
оставлен как история.

ТЗ на редизайн интерфейса для дизайнера — `docs/TZ_REDESIGN.md`: роли,
процесс, все экраны и компоненты, токены, правила и чек-лист приёмки.
Скриншоты текущего интерфейса «как есть» — `docs/screens/current/`.

> В дизайн-хендоффе система называется **CORE** — так её назвали на этапе
> макетов. Заказчик выбрал имя **ORDER**, под ним же домен
> `order.ithona.tj`. Файлы в `docs/` оставлены как есть, это исходные
> документы; в продукте везде ORDER.

## Как устроен обмен

```
браузер ──▶ nginx ──┬──▶ /            статика панели (React)
                    └──▶ /api, /health  FastAPI ──▶ PostgreSQL
```

Панель и API отдаются с одного origin, поэтому CORS не нужен.

## Выгрузки

| Что | Формат | Откуда | Кому |
|---|---|---|---|
| Реестр выплат за период | Excel, PDF | Отчёты | руководитель, финансы, админ |
| Список заявок по фильтру | Excel | Панель, Заявки | всем, каждому — своё |
| Одна заявка для подшивки | PDF | карточка заявки | тому, кто её видит |
| Журнал действий по фильтру | Excel | Журнал | админ |

Дата выплаты не принимается из будущего и не может быть раньше решения по
заявке: иначе закрытый месяц уезжает, а исправить нечем — история заявок
неизменяема.

Выгрузка не обходит права: сотрудник получает файл только со своими
заявками, ограничение навязывает сервер.

В Excel суммы кладутся числами с денежным форматом, а не строками — иначе
получатель не просуммирует столбец. Гарнитура Arial: брендбук запрещает
отдавать клиенту фирменные шрифты в офисных файлах.

PDF собирается со встроенными шрифтами Manrope и JetBrains Mono. Они лежат
в `backend/app/assets/fonts` и пересобираются скриптом:

```bash
cd backend
pip install "fonttools[woff]"
python scripts/build_pdf_fonts.py
```

Скрипт склеивает подмножества из npm-пакетов `@fontsource` и добирает
таджикские буквы `ғ ӣ қ ӯ ҳ ҷ` из Noto Sans: в Manrope их нет, поэтому
брендбук и требует эту пару. Файлы коммитятся в репозиторий — на сервере
`node_modules` нет, а образ должен собираться без интернета. Лицензии —
`backend/app/assets/fonts/LICENSE.md`.

## Вход

Войти можно только с корпоративной почты (`ALLOWED_EMAIL_DOMAINS`,
по умолчанию `@ithona.tj`). Личные ящики не проходят ни при заведении
сотрудника, ни при входе: почта здесь одновременно логин и подтверждение,
что человек работает в компании.

> **`ALLOWED_EMAIL_DOMAINS` — это домен почты, а не домен панели.**
> Укажите тот, в котором реально заведены ящики в Zoho. Ошибка здесь
> закрывает вход всем, включая администратора: адрес стартового
> администратора тоже проверяется по этому списку.

**Двухфакторный вход** — код из приложения-аутентификатора (Google
Authenticator, Aegis, 1Password и любое другое, TOTP по RFC 6238).
Администраторам и финансам он обязателен (`REQUIRE_2FA_ROLES`), остальные
включают его по желанию в «Параметрах».

```
почта + пароль ──▶ код из приложения ──▶ сессия
                   (или код восстановления)
```

Между шагами выдаётся отдельный короткоживущий токен: доступа к данным он
не даёт и сессионный не подменяет.

При включении выдаются 10 кодов восстановления — на случай потери телефона.
Они показываются один раз: в базе хранятся только отпечатки. Если потеряны
и они, второй фактор сбрасывает администратор
(`POST /api/employees/{id}/reset-2fa`).

Секрет второго фактора хранится зашифрованным ключом, выведенным из
`SECRET_KEY`, поэтому утечка одного лишь дампа базы не позволит генерировать
чужие коды. Использованный код не принимается повторно в своём
30-секундном окне. После `MAX_FAILED_LOGINS` неудач подряд вход временно
блокируется: без этого шестизначный код подбирается за часы.

> **Смена `SECRET_KEY` делает существующие секреты второго фактора
> нечитаемыми.** Всем, у кого он включён, придётся настроить его заново
> через сброс администратором. Не меняйте ключ без необходимости.

## Почта

Отправка идёт через Zoho Mail. Что важно при настройке:

- **Сервер зависит от региона аккаунта**: `smtp.zoho.com` (США),
  `smtp.zoho.eu` (Европа), `smtp.zoho.in`, `smtp.zoho.com.au`,
  `smtp.zohocloud.ca`. Неверный регион даёт ошибку аутентификации, хотя
  логин и пароль правильные.
- **Нужен пароль приложения**, а не пароль от аккаунта: Zoho → Мой аккаунт →
  Безопасность → Пароли приложений. С включённым вторым фактором обычный
  пароль SMTP не примет.
- **Адрес отправителя** должен принадлежать проверенному в Zoho домену.
- **`PUBLIC_BASE_URL`** обязателен: без него ссылку восстановления пароля
  в письме некуда вести.

Проверить настройку: администратор нажимает «Отправить проверочное письмо»
в «Параметрах» либо вызывает `POST /api/mail/test` — письмо придёт ему
самому, а ошибка SMTP вернётся с причиной, а не потеряется.

Письма уходят в фоне и никогда не отменяют действие: заявка подаётся,
даже если почтовый сервер недоступен. Неудача попадает в журнал.

Что отправляется сейчас:

| Событие | Кому |
|---|---|
| Заявка ждёт решения | согласующим, кроме автора заявки |
| Восстановление пароля | по запросу, на корпоративный адрес |
| Проверочное письмо | администратору, по кнопке |
| Заявка стоит без движения | тому, у кого она стоит (раз в сутки, одним списком) |
| Итоги недели | по понедельникам тем, кто видит отчёты и включил сводку |

Последние две уходят и в Telegram — каждому по тому, что у него подключено;
как это работает, в разделе «Напоминания и сводка».

## Напоминания и сводка

Заявка не двигается сама. Если она третий день лежит у одного человека, об
этом узнаёт он — не автор, который уже всё сделал.

- **Напоминание о залежавшихся заявках** — каждый день в `REMINDER_HOUR`
  (по умолчанию 09:00 по Душанбе). Уходит тому, у кого заявка стоит сейчас:
  руководителю, закупу, бухгалтерии, а по забытому черновику — автору.
  Одно письмо на человека со списком, а не письмо на заявку. Порог —
  `STALE_REQUEST_DAYS` суток на одном шаге, по умолчанию три. Свою заявку
  человек всё равно не двигает, поэтому она в его напоминание не попадает.
- **Итоги недели** — по понедельникам в тот же час: подано, выплачено,
  бюджет месяца, сколько заявок стоит без движения. Только тем, кто видит
  отчёты И включил сводку в «Параметрах» (по умолчанию выключена).

Обе рассылки идут и письмом, и в Telegram — каждому по тому, что у него
подключено. Переключатели в «Параметрах» у каждого свои.

Планировщик живёт в процессе `api`: отдельный контейнер ради двух задач в
сутки не нужен. Раз в минуту он спрашивает, чему пришло время, и занимает
день под задачу уникальным ключом в таблице `job_runs` — поэтому
перезапуск контейнера или второй процесс не разошлют одно и то же дважды.

Сервер лежал в назначенный час — задача выполнится позже, но не позже чем
через `SCHEDULER_CATCH_UP_HOURS` (по умолчанию 6). Дальше день закрывается
со статусом `SKIPPED`: напоминание в полночь никому не нужно.

Администратор видит последние запуски в «Параметрах» → «Фоновые задачи» и
может запустить рассылку сейчас — так проверяют настройку почты и бота, не
дожидаясь утра. Ручной запуск пишется и в журнал действий.

## Установка на телефон

Панель — PWA: её ставят на экран телефона как обычное приложение, со
своей иконкой и без адресной строки. «Параметры» → «Приложение на
телефоне»: на Android (Chrome) там кнопка «Установить на экран», на
iPhone — подсказка «Поделиться → На экран «Домой»» (кнопки у Safari нет).
Ярлык приложения «Новая заявка» открывает форму сразу
(`/requests?new=1`).

Что для этого есть в сборке: `public/manifest.webmanifest`, иконки из
фирменного знака в `public/icons/`, service worker `public/sw.js` и
заглушка `public/offline.html`. Воркер кэширует только хэшированные
ассеты и показывает заглушку при обрыве связи; данные из API не
кэшируются никогда — устаревшая заявка на экране хуже отсутствующей.
Версия воркера подставляется при сборке (`vite.config.ts`), поэтому
после обновления сервера старый кэш сбрасывается сам; nginx отдаёт
`sw.js` с `no-store`, иначе старый воркер пережил бы обновление.

## Уведомления на телефон (push)

Панель, поставленная на экран, получает push-уведомления как обычное
приложение: судьба своих заявок, заявки, которые ждут вас, напоминания о
залежавшихся и недельная сводка — те же сообщения, что уходят в Telegram
и на почту. Работает на Android (Chrome) и на iPhone с iOS 16.4+ — но
только у панели, поставленной на экран: во вкладке Safari push не
существует, и карточка в «Параметрах» так и говорит.

Настройка — один ключ:

```bash
docker compose exec api python -m app.push_setup          # печатает VAPID_PRIVATE_KEY для .env
docker compose exec api python -m app.push_setup --check  # что настроено
```

Ключ вписать в `.env` и пересоздать контейнер: `docker compose up -d api`
(`restart` новые переменные не перечитывает). Дальше каждый сотрудник
включает уведомления сам:
«Параметры» → «Уведомления на телефоне» → «Включить уведомления»,
браузер спросит разрешение. Кнопка «Проверить» шлёт проверочное
уведомление на все устройства человека. Одна подписка — один браузер,
подписок у сотрудника может быть несколько. Подписка, которую push-служба
объявила отозванной (телефон снял приложение с экрана), удаляется сама
при первой же попытке отправки.

Смена `VAPID_PRIVATE_KEY` обнуляет подписки всех телефонов: люди увидят
«Включить уведомления» заново. Сбой push никогда не отменяет действие с
заявкой — как и сбой почты или бота.

## Помощник по заявке (AI)

Кнопка «Помощь AI» у блока позиций открывает диалог. Сотрудник пишет как
умеет — «нужен кабель на камеры Регар», «2 buhta utp cat6 regar», —
помощник задаёт один-три коротких вопроса с готовыми вариантами (тип
кабеля, внутренний или наружный, метраж) и в конце показывает готовые
позиции: наименование с характеристиками, количество, единицу и
назначение. Кнопка «Применить в заявку» переносит их в форму; ничего не
подставляется молча и заявка сама не отправляется.

Если позиции уже введены, кнопка называется «Проверить заявку»: помощник
скажет, чего не хватает закупу, и что стоит уточнить.

Помощник видит контекст формы (объект, автора, введённые позиции) и
каталог уже заказанного, поэтому не спрашивает то, что и так известно, и
предлагает принятые в компании написания. Цены он не обсуждает: их
ставит отдел закупа.

Проверить помощника на сервере:

```
docker compose exec api python -m app.assistant_check
```

Команда делает один настоящий запрос и печатает причину отказа с
подсказкой: кончились кредиты, не подошёл ключ, не хватило времени.
Ключ не печатается. Ответ модели в диалоге занимает десятки секунд,
поэтому срок ожидания по умолчанию 90 секунд (`ASSISTANT_TIMEOUT_SECONDS`),
а nginx ждёт ответ помощника до 300 секунд.

Правила помощника живут в `backend/app/services/assistant_prompt.py`. Их
можно заменить, не пересобирая образ: положить текст в файл и указать
путь в `ASSISTANT_PROMPT_FILE`.

## Помощник по материалам

В форме заявки, когда сотрудник закончил печатать название материала,
помощник на Claude проверяет написание и предлагает поправку:
«гофра16» → «Гофра 16 мм», единица «м», подсказка «укажите тип: ПВХ или
металл». Если такое уже заказывали, предлагается написание из каталога,
чтобы один материал не расползался на пять вариантов в отчётах и
подсказках. Совет применяется кнопкой — молча текст не переписывается.

Включается одним ключом в `.env`:

```
ANTHROPIC_API_KEY=sk-ant-...     # console.anthropic.com → API keys
ASSISTANT_MODEL=claude-opus-5    # по умолчанию, менять не обязательно
```

и `docker compose up -d api`. Без ключа помощник выключен, форма
подсказывает только то, что уже заказывали. Сбой модели никогда не
мешает подать заявку: подсказка просто не показывается. Одинаковые
вопросы кэшируются в памяти процесса, чтобы не платить за каждое
повторение.

Стоимость: один вопрос — примерно тысяча токенов на вход (каталог
материалов) и сотня на выход, то есть меньше цента. При ста строках в
день это около доллара в месяц.

## Заявка из Telegram

На стройке телефон под рукой, а панель — нет. Мастер стоит на объекте и
браузер, чтобы попросить два мешка цемента, открывать не станет: заявка,
которую не подали, — это купленный за свои материал и испорченный отчёт.
Поэтому бот умеет не только писать, но и принимать заявки.

```
/new     подать заявку
/cancel  прервать начатую
/help    что умеет бот
/stop    отключить уведомления
```

Разговор короткий: объект (кнопками) → «что нужно» словами → до трёх
уточнений с готовыми вариантами → карточка подтверждения с кнопками
«Отправить на согласование», «Изменить», «Отмена». Цены указывать не
надо — их поставит закуп.

Три вещи, которые здесь важны:

- **Заявку создаёт тот же сервис, что и панель** (`services/requests.py`).
  Второго пути создания заявки в системе нет и не будет: иначе однажды
  правила разойдутся, и никто не поймёт почему.
- **Без подтверждения не уходит ничего.** Последнее нажатие всегда за
  человеком — как кнопка «Применить» в панели.
- **Права те же, что в панели**, и роль перечитывается из базы на каждом
  сообщении: отключённому сотруднику бот откажет, даже если разговор
  начался вчера. Заявку за другого через бота подать нельзя.

Если помощник недоступен (нет ключа, кончился баланс), бот не закрывается:
он записывает написанное одной позицией и просит проверить количество.
Разговор без ответа протухает через сутки.

Настройка та же, что для уведомлений: «Параметры» → «Настроить бота на
этот сервер» или `docker compose exec api python -m app.telegram_setup`.
Нажатия кнопок приходят отдельным типом обновления, поэтому после
обновления версии вебхук нужно переустановить — иначе карточка
подтверждения будет нажиматься, но молчать.

## Память заявок: подсказки из истории

ORDER помнит, что уже заказывали, и подсказывает это в форме — **без
всякой модели**. Считает подсказки база (`app/services/ai_memory.py`),
поэтому они работают, даже когда помощник выключен: кончился баланс у
Anthropic, а автодополнение осталось на месте.

- **«Часто заказываете»** — лента под позициями. Порядок источников от
  точного к общему: что берут на выбранном объекте, потом что заказывает
  сам сотрудник, потом что просят в компании. Нажатие подставляет
  наименование и единицу — самая частая заявка это повтор прошлой.
- **Похожие заявки.** Как только в форме есть позиция и объект, панель
  спрашивает, не подавали ли то же самое за последнюю неделю, и
  показывает номера с датами. Это подсказка, а не запрет: нужно ещё —
  подавайте. Две одинаковых заявки обычно замечают тогда, когда обе уже
  оплачены.
- **Одно написание — один материал.** У строки заявки два написания:
  `title` — как написал человек (его и показываем всегда) и
  `normalized_text` — приведённое (`app/services/material_norm.py`), по
  нему идут поиск, подсчёт и сравнение. «гофра16», «Гофра 16мм» и
  «ГОФРА 16 ММ.» — один материал, а не три.
- **Алиасы копятся сами.** Когда человек нажимает «Применить» на совете
  помощника, поправка запоминается в `material_aliases`. Следующему
  сотруднику она придёт мгновенно и бесплатно, без обращения к модели.
  Руками эту таблицу никто не ведёт: справочник, который надо
  поддерживать, устареет за месяц — так в ORDER решено с самого начала.

Права те же, что у заявок. Названия материалов общие: иначе новый
сотрудник не получил бы ни одной подсказки в первый день. А «кто, когда
и на сколько заказывал» — это чужая заявка: без права `view_all_requests`
человек видит в «своём» и в повторах только себя.

## Журнал обращений к AI

Помощник стоит денег и работает не всегда одинаково. Чтобы это было
видно, каждое обращение пишется в `ai_interactions`: кто спросил, о чём,
ответила ли модель, сколько ждали и — главное — нажал ли человек
«Применить». Ответ, который никто не применяет, помощником не является.

Смотреть — «Параметры» → «Помощник AI» (право `manage_reference`, то есть
администратор): состояние, модель, ключ маской, доля отвеченных
обращений за 30 дней, среднее время ответа и последние обращения с
причинами отказов.

Чего в журнале нет: ключа Anthropic и любых секретов. В базу попадает
только то, что человек и так видел на экране, обрезанное по длине.
Модели эта таблица не показывается никогда — память помощника это сами
заявки, а не его прошлые ответы.

## AI-аналитика для руководителя

Раздел «Аналитика AI» (право `view_reports`: руководитель, финансы,
администратор) отвечает на вопрос «что происходит и на что смотреть».

- **Сводка.** Заявки, вышедшие за норматив этапа, с причиной у каждой:
  «стоит 31 ч при норме 8 ч», «некому решить: нет активных сотрудников
  роли», «похожа на другую заявку того же объекта».
- **Этапы.** Где стоят заявки, сколько ждут, укладываются ли в норматив
  и сколько этап занимал фактически за месяц против прошлого.
- **Похожие заявки.** Повторы одного объекта за неделю по совпавшим
  позициям. Ничего не удаляется: решает человек.
- **Объекты и люди.** Сколько заявок и денег по объектам; кто сколько
  держит сейчас. Про людей — только факты, без оценок работы.
- **Спросить ORDER AI.** Вопрос обычными словами: «какие заявки
  зависли», «что изменилось за неделю». Ответ со ссылками на заявки.

**Все числа считает сервер.** Модель получает готовые факты и объясняет
их словами; ни одна цифра в сводке не приходит от модели. Поэтому
раздел работает и без ключа Claude — просто без пояснений.

Нормативы этапов задаются в `.env` (`SLA_PENDING_HOURS` и остальные),
правила аналитика — файлом `ANALYTICS_PROMPT_FILE`, без пересборки.
Вопросы руководителей пишутся в журнал действий: аналитика показывает
данные всей компании.

Чего система не знает и о чём честно говорит: накладных и чеков файлами
в ORDER нет (выплата всегда проводится ровно на сумму заявки), отделов
нет — их роль играют этапы, приоритета заявки и возврата на доработку
тоже нет.

## Telegram

Бот пишет автору заявки на каждом шаге и зовёт того, к кому заявка пришла.
Работает параллельно с почтой и ничего в ней не меняет: не настроен —
уведомлений в Telegram просто нет.

Настройка:

1. В Telegram: `@BotFather` → `/newbot` → имя и `@имя` бота. Полученный
   токен — `TELEGRAM_BOT_TOKEN`, `@имя` без собачки — `TELEGRAM_BOT_USERNAME`.
2. Перезапустить сервисы и выполнить на сервере:

   ```bash
   docker compose exec api python -m app.telegram_setup
   ```

   Команда проверяет токен, сообщает Telegram адрес вебхука
   `PUBLIC_BASE_URL/api/telegram/webhook/<секрет>` и показывает состояние
   доставки. Секрет выводится из `SECRET_KEY`, отдельной переменной нет.
   То же самое делает кнопка **«Настроить бота на этот сервер»** в
   «Параметрах» — команда удобнее при разборе неполадок, потому что
   печатает причину отказа Telegram целиком.

   Только проверить, ничего не меняя: `python -m app.telegram_setup --check`.
3. Каждый сотрудник подключает себя сам: «Параметры» → «Подключить
   Telegram» → открывается бот → «Старт».

Панель не спрашивает ни номер телефона, ни id чата: она выдаёт одноразовую
ссылку `https://t.me/<бот>?start=<код>`, код живёт полчаса и срабатывает
один раз. Id чата приходит от самого Telegram, когда человек нажимает
«Старт». Один чат принадлежит одному сотруднику — привязать его второму
бот откажется, иначе кто-то тихо перестал бы получать уведомления.

Отключить: кнопка «Отключить» в «Параметрах» или команда `/stop` боту.

**Если бот молчит**, начинайте с `python -m app.telegram_setup --check`: он
отвечает на все три вопроса сразу — принят ли токен, куда Telegram шлёт
обновления и не было ли ошибок доставки. Молчание бота на `/start` почти
всегда означает, что вебхук не установлен: даже для чужого чата бот
отвечает «этот чат ни к кому не привязан».

| Событие | Автору | Тому, к кому пришла |
|---|---|---|
| Подана | «отправлена на согласование покупки» | руководителю |
| Согласована покупка | «передана в отдел закупа» | закупу |
| Закуп проставил цены | «сумма ушла руководителю» | руководителю |
| Сумма утверждена | «передана в бухгалтерию на оплату» | бухгалтерии |
| Оплачена, закрыта складом, отклонена | итог (при отказе — с причиной) | — |

> **`.env` должен быть с обычными переводами строк.** Файл переносят через
> Windows, и он приезжает с CRLF — лишний невидимый символ попадает в конец
> токена, и Telegram отвечает «malformed URL», а SMTP — отказом в логине при
> верном пароле. Проверяет `./deploy/check-env.sh`, чинит
> `sed -i 's/\r$//' .env`. Приложение с версии 0314a6e срезает такие
> хвосты само, но старый контейнер об этом не знает — перезапустите.

> Сервер должен быть доступен Telegram по https: вебхук приходит снаружи.
> После смены `PUBLIC_BASE_URL` или `SECRET_KEY` кнопку настройки нужно
> нажать заново — старый адрес перестанет совпадать.

Сообщения уходят в фоне и, как письма, никогда не отменяют действие: бот
молчит — заявка всё равно подана и согласована, а неудача попадает в лог.

### Восстановление пароля

```
запрос по адресу ──▶ письмо со ссылкой ──▶ новый пароль
```

Ответ на запрос одинаков для существующего и несуществующего адреса: разный
выдал бы, кто заведён в системе. Ссылка живёт `PASSWORD_RESET_TTL_MINUTES`
и срабатывает один раз — в токен зашит отпечаток текущего пароля, и смена
пароля гасит все выданные ссылки.

**Второй фактор смена пароля не обходит.** Ссылка не выдаёт сессию, а вход
по новому паролю всё равно потребует код из приложения. Доступа к почте
недостаточно, чтобы попасть в систему.

## Роли и права

| | Сотрудник | Руководитель | Закуп | Финансы | Администратор |
|---|:---:|:---:|:---:|:---:|:---:|
| Подать свою заявку | ✅ | ✅ | ✅ | ✅ | ✅ |
| Видеть чужие заявки | — | ✅ | ✅ | ✅ | ✅ |
| Согласовать покупку и сумму | — | ✅ | — | — | ✅ |
| Проверить склад, поставить цены | — | — | ✅ | — | ✅ |
| Провести выплату | — | — | — | ✅ | ✅ |
| Отчёты, команда, бюджет | — | ✅ | — | ✅ | ✅ |
| Справочники, роли и пароли | — | — | — | — | ✅ |
| Журнал действий | — | — | — | — | ✅ |
| Видеть состояние доступа коллег | — | — | — | — | ✅ |
| Подать заявку за другого | — | — | — | — | ✅ |

Разделение обязанностей: кто согласовал — тот не платит, и собственную
заявку не согласуют и не оплачивают даже с правом решения. У администратора
есть оба права, поэтому проверка стоит на самом запросе: одобрил — выплату
проводит кто-то другой. Автоодобрение выполняет система, такие заявки
оплачивает кто угодно с правом выплаты. Права описаны одной таблицей
в `backend/app/core/permissions.py` и проверяются сервером на каждом
запросе; панель по ним лишь прячет разделы.

Список сотрудников читает любой вошедший — без него не заполнить заявку.
А кто когда входил, у кого задан пароль и включён ли второй фактор, отдаёт
отдельный `GET /api/employees/access`, закрытый правом на справочники:
коллегам эти сведения ни к чему.

Сотрудник видит только свои заявки. Фильтр по автору навязывает сервер,
поэтому подмена параметра в адресной строке ничего не даёт, а чужая заявка
по прямой ссылке отвечает 404, а не 403 — иначе по коду ответа можно было бы
перебрать чужие номера.

## Жизненный цикл заявки

```
DRAFT ─отправить─▶ PENDING ─согласовать покупку─▶ SOURCING ─оценить─▶ PRICED
                                                     │                  │
                                        всё со склада └──▶ FULFILLED    │
                                                                        │
                                        PRICED ─утвердить сумму─▶ APPROVED ─оплатить─▶ PAID
```

Сотрудник описывает **потребность без цен**: что нужно, сколько и в чём
считать. Цены он знать не обязан — их назовёт отдел закупа.

1. **Руководитель** согласует саму покупку: нужна ли она вообще.
2. **Отдел закупа** проверяет склад. Что нашлось — закрывает складом
   (денег по этим строкам нет), на остальное ставит цены.
3. **Руководитель** утверждает сумму, которую назвал закуп.
4. **Бухгалтерия** проводит выплату.

Нашлось всё на складе — заявка закрывается статусом «Выдано со склада»,
оплаты не будет. Часть строк со склада, часть покупаем — заявка идёт
дальше на сумму того, что покупаем.

Автоодобрения по сумме нет: сумму всегда утверждает руководитель, какой бы
маленькой она ни была. Отказ возможен на любом из двух его шагов.

В списке заявок и в карточке видно, **у кого заявка сейчас**: «у
руководителя», «у закупа», «в бухгалтерии» — и сколько суток она там лежит.
В карточке перечислены поимённо те, кто может сделать следующий шаг:
персональных назначений в системе нет, заявку берёт любой, у кого есть
право, а автор в этот список не попадает — свою заявку он не согласует, не
оценивает и не оплачивает.

Обратных переходов нет: ошибочное решение исправляется новой заявкой,
история неизменяема. Править состав можно только у черновика.

## Разделы панели

Панель · Заявки · Согласование · Отчёты · Команда · Финансы · Сотрудники ·
Объекты · Журнал · Параметры · Справка, плюс внутренняя страница-эталон «Дизайн-система»
(`/system`).

Заявку подают кнопкой «Создать заявку» на дашборде и в «Заявках»: объект и
строки «что нужно — сколько — в чём» (мешок, шт., м²). Цен в форме нет.
«Отправить на согласование» — заявка уходит руководителю, «Сохранить
черновиком» — остаётся у автора. В карточке черновика его можно
изменить, отправить или удалить; поданную заявку править нельзя.

В поле «что нужно» работает подсказка: панель предлагает то, что уже
заказывали, и подставляет единицу измерения из прошлой заявки. Справочника
материалов нет и заводить его не нужно — список собирается из самих заявок
и всегда отражает то, чем реально пользуются. Разные написания одного и
того же («хомут» и «Хомут») схлопываются, показывается свежее.

**Закуп** — раздел отдела закупа: очередь заявок, чью покупку уже
согласовал руководитель. По каждой строке либо цена за единицу, либо
отметка «есть на складе»; итог считается на глазах. Кнопка называется
«Отправить руководителю», а если всё нашлось на складе — «Закрыть складом».

**Согласование** у руководителя разделено на две вкладки: «Покупка» —
согласовать саму необходимость, «Сумма» — утвердить то, что насчитал закуп.
Утверждённую заявку финансы проводят прямо в её карточке: способ, номер
документа, «Провести выплату». С «Финансов» к очереди одобренных ведёт
ссылка `/requests?status=approved`.

**Объекты** — справочник строек и площадок, на которые списываются расходы;
тоже только для администратора. Завести, переименовать, отключить. Рядом с
каждым объектом видно число заявок и расход по нему. Удаления нет: объект
попадает в заявки, а они неизменяемы и должны сохранить, на что был расход, —
закрытый объект отключают, и он пропадает из выбора при подаче новой заявки.

**Журнал** тоже только для администратора: кто входил и выходил, чьи
попытки входа не прошли и когда сработала блокировка, кто одобрил и оплатил
заявку, кто правил справочники. Для каждой записи — время, имя, действие,
затронутая запись и адрес, с которого пришёл запрос. Есть фильтры по
разделу, действию, сотруднику и датам, поиск и выгрузка в Excel. Записи
журнала не редактируются и не удаляются — ни в панели, ни через API.

**Сотрудники** видны только администратору. Раздел ведёт справочник людей и
их доступ: завести коллегу, назначить роль, выдать или
заменить пароль, увидеть, кто может входить и у кого включён второй фактор,
сбросить второй фактор потерявшему телефон, отключить уволенного. Уволенного
отключают, а не удаляют: заявки неизменяемы и должны сохранить автора —
удаление доступно только для записи без заявок. Последнего активного
администратора система не даст ни разжаловать, ни отключить, ни удалить:
иначе справочники и пароли станут недоступны никому.

В шапке сайдбара стоит горизонтальная композиция фирменного логотипа
IT-HONA, на экране входа и при восстановлении пароля — основная,
вертикальная. Белый вариант на тёмном сайдбаре, зелёный на светлом.
Геометрия из официальных файлов бренд-пакета (`docs/brand/`), набранного
словами названия в интерфейсе больше нет.

Каркас один: тёмно-зелёный сайдбар со счётчиком очереди согласования,
топбар с поиском по заявкам (номер, объект, автор, позиции) и
переключателем светлой и тёмной темы. Карточка заявки — отдельная
страница с лентой этапов и блоком «Сейчас ждёт»; там же руководитель
решает, закуп ставит цены, бухгалтерия проводит выплату, а автор двигает
черновик.

### Как убедиться, что панель обновилась

Внизу сайдбара рядом с версией стоит дата сборки — `v1.0 · 09-08`. Если
после обновления сервера дата прежняя, браузер показывает старую версию из
кэша: обновите страницу с Ctrl+Shift+R (на Mac ⌘+Shift+R). Сам nginx
index.html не кэширует, но вкладка, открытая до обновления, продолжает
работать на старом коде, пока её не перезагрузить.

## Первый запуск

```bash
cp .env.example .env      # заполнить POSTGRES_PASSWORD, при желании SECRET_KEY
mkdir -p data/postgres
docker compose up -d --build
```

Панель поднимется на порту из `WEB_PORT` (по умолчанию 8080). PostgreSQL и API
наружу не публикуются: снаружи доступен только nginx. Миграции применяются
автоматически при старте контейнера `api`, под advisory-локом.

### Первый вход

Войти можно только зарегистрированным пользователем, а завести пользователя
может только вошедший администратор. Этот круг разрывает стартовый
администратор: заполните в `.env` перед первым запуском

```
BOOTSTRAP_ADMIN_EMAIL=admin@ithona.tj
BOOTSTRAP_ADMIN_PASSWORD=длинная-фраза-минимум-десять-символов
```

Он создастся при старте, если в базе нет ни одного администратора с паролем.
**После первого входа смените пароль и удалите эти строки из `.env`.**

Дальше администратор заводит сотрудников в разделе «Сотрудники»: кнопка
«Добавить сотрудника», при заведении можно сразу сгенерировать пароль.
Карточка и пароль уходят одним запросом: либо сотрудник заведён и может
войти, либо не заведён вовсе — половинчатых записей без доступа не бывает. Пароль
показывается один раз — в базе хранится только хэш, поэтому передайте его
лично и попросите сменить в «Параметрах». То же самое из API:
`POST /api/employees` и `PUT /api/employees/{id}/password`.


Скрипт добавляет 4 объекта, 11 сотрудников и 10 заявок в разных статусах.
Все демо-учётные записи получают пароль `hona-demo-2026`. Адреса берут
первый домен из `ALLOWED_EMAIL_DOMAINS`, то есть при настройке по умолчанию:
администратор `admin@ithona.tj`, руководитель `a.kovalev@ithona.tj`,
финансы `n.rahimova@ithona.tj`, сотрудник `i.petrov@ithona.tj`.

**В рабочую базу не запускать:** данные условные, пароль общеизвестный.
Повторный запуск на непустой базе ничего не делает.

## Проверки перед коммитом

```bash
cd backend  && pytest              # нужна пустая база hona_core_test
cd frontend && npm run build       # tsc + vite
cd frontend && npm run preview &   # порт 4173, API должен быть на :8000
cd frontend && npm run smoke       # вход под каждой ролью и обход разделов
cd frontend && npm run mobile      # то же на экране телефона (iPhone 13)
```

`pytest` работает на настоящей PostgreSQL: SQLite не воспроизводит поведение
NUMERIC, timestamptz и ограничений, ради которых тесты и написаны. Заведите
базу `hona_core_test` — схему тесты создают сами.

`npm run mobile` открывает панель в экране 390 px и падает, если хоть одна
страница прокручивается вбок: с горизонтальной прокруткой половина таблицы
уезжает за край, и человек её просто не находит. Заодно снимает скриншоты в
`.shots/mobile` — по ним видно, что получилось, а не только что ничего не
сломалось.

`npm run smoke` входит под руководителем, финансами и сотрудником, обходит
доступные каждой роли разделы, проверяет, что лишние пункты меню не видны,
снимает скриншоты в `.shots/` и падает при ошибке в консоли или ответе
4xx/5xx. Работает на демонстрационных данных: путь к браузеру — `PW_CHROMIUM`,
пароль — `SMOKE_PASSWORD`.

Для разработки по http поставьте `COOKIE_SECURE=false`, иначе браузер не
сохранит cookie сессии и вход не сработает.

## Миграции

Схема меняется только миграциями Alembic, `create_all()` в рантайме запрещён.

```bash
cd backend

```

Ревизии нумеруются подряд: `0001`, `0002`, … Перед коммитом прогоните

обратимой.

## Развёртывание на сервере

Целевой сервер: Ubuntu 22.04, 2 ядра, 2 ГБ RAM, 30 ГБ SSD.

### 1. Подготовка системы

```bash
# Если apt ругается на прерванный dpkg — сначала это:
dpkg --configure -a

apt update && apt upgrade -y
ufw allow OpenSSH && ufw allow 80 && ufw allow 443 && ufw enable
curl -fsSL https://get.docker.com | sh
```

Порт панели (8080) в фаерволе **не открывается**: снаружи работает только
Caddy на 80 и 443, а панель слушает на `127.0.0.1`.

Работать под root не нужно — заведите пользователя и вход по ключу:

```bash
adduser hona && usermod -aG docker,sudo hona
mkdir -p /home/hona/.ssh && cp ~/.ssh/authorized_keys /home/hona/.ssh/
chown -R hona:hona /home/hona/.ssh && chmod 700 /home/hona/.ssh
# После проверки входа под hona отключите вход root по паролю:
#   PermitRootLogin prohibit-password  в /etc/ssh/sshd_config
```

### 2. Домен

Заведите A-запись на IP сервера — `order.ithona.tj`. Без домена
сертификат Let's Encrypt не выпустить, а `COOKIE_SECURE=true` требует HTTPS
— по обычному http браузер не сохранит cookie сессии и вход не сработает.

Проверить, что запись разошлась: `dig +short order.ithona.tj`

### 3. Проект и настройки

```bash
git clone https://github.com/khudoyorparpishoev0-ops/IT-ORDER.git /opt/hona-order
cd /opt/hona-order
cp .env.example .env
mkdir -p data/postgres data/backups data/caddy data/caddy-config
```

Заполните в `.env` обязательное:

```bash
POSTGRES_PASSWORD=$(openssl rand -base64 32)
SECRET_KEY=$(openssl rand -hex 32)
APP_DOMAIN=order.ithona.tj
ACME_EMAIL=admin@ithona.tj
PUBLIC_BASE_URL=https://order.ithona.tj
BOOTSTRAP_ADMIN_EMAIL=admin@ithona.tj
BOOTSTRAP_ADMIN_PASSWORD=длинная-фраза-минимум-десять-символов
```

Плюс почта Zoho (см. раздел «Почта») — без неё письма не отправляются,
но система работает.

Проверьте конфигурацию перед запуском:

```bash
./deploy/check-env.sh
```

Скрипт ловит две ошибки, которые иначе всплывают уже после запуска:
повтор ключа (при дубле docker compose берёт **последнее** значение,
поэтому случайно вставленная пустая строка перебивает заполненную выше)
и незаполненное обязательное значение.

Правьте `.env` только в редакторе, вставляя значения **в существующие
строки**. Дописывание блоков в конец файла создаёт дубли.

### 4. Запуск

`COMPOSE_FILE` в `.env` уже перечисляет оба файла, поэтому длинных ключей
`-f` не нужно:

```bash
docker compose up -d --build
docker compose logs -f caddy   # ждём выпуска сертификата
curl -s https://order.ithona.tj/health
```

Первая сборка на 2 ГБ RAM занимает несколько минут. Если сборка фронтенда
упирается в память — соберите образ на рабочей машине и перенесите готовый.

Войдите под стартовым администратором, **смените пароль, настройте второй
фактор и удалите `BOOTSTRAP_ADMIN_*` из `.env`.**

### 5. Резервные копии

```bash
./deploy/backup.sh
crontab -e
# 20 3 * * * cd /opt/hona-order && ./deploy/backup.sh >> data/backup.log 2>&1
```

Копии складываются в `data/backups`, старше `BACKUP_KEEP_DAYS` удаляются.
Восстановление: `./deploy/restore.sh data/backups/hona_core_ГГГГ-ММ-ДД_ЧЧ-ММ.sql.gz`
— скрипт спрашивает подтверждение, потому что заменяет текущие данные.

**Копии на самом сервере — это не резервное копирование.** Настройте
выгрузку `data/backups` наружу: на Synology, в объектное хранилище или хотя
бы `rsync` на другую машину. Диск сервера может умереть вместе с копиями.

### 6. Обновление

```bash
cd /opt/hona-order
./deploy/backup.sh                 # сначала копия
git pull origin main
docker compose up -d --build
```

Миграции применяются автоматически при старте контейнера `api`, под
advisory-локом.

Поменяли что-то в `.env` — выполните `docker compose up -d`, а не
`docker compose restart`: перезапуск поднимает тот же контейнер с прежним
окружением, новые значения он не видит. `up -d` пересоздаёт только те
контейнеры, у которых изменилось окружение.

## Правила, которые нельзя нарушать

- Токены только из `frontend/src/styles/tokens.css`. Новых цветов и радиусов в
  компонентах не заводить.
- Шрифты ставятся из npm и хостятся приложением. CDN запрещён.
- Статус всегда цвет **и** слово. Круглых аватаров, «таблеток» и тумблеров нет.
- Числа в формате ru-RU: `1 250 000,00`. Валюта — в заголовке столбца
  (`СУММА, TJS`) или словом «сомони».
- Секреты только в `.env`. В логи не писать пароли и токены.

## Предположения, которые нужно подтвердить

Эти решения приняты, чтобы не останавливать работу. Переделать их дёшево.

- **Согласование одноступенчатое:** решение принимает один руководитель.
  Цепочки из нескольких согласующих нет — если она нужна, скажите.
- **Выплату проводят финансы**, а не тот, кто согласовал.
- **Заявку за другого подаёт только администратор.** Автор заявки должен быть
  настоящим: иначе непонятно, чей это расход и чей лимит расходуется.
- **Одна заявка — одна выплата**, частичное возмещение не предусмотрено.
- **Срок сессии — 12 часов**, меняется в `SESSION_LIFETIME_MINUTES`.
- **Второй фактор — приложение-аутентификатор, а не коды на почту.** Почта
  здесь первый фактор: код из того же ящика защищал бы только от
  подсмотренного пароля, но не от взломанной почты.
- **Письма отправляются в фоне, без очереди и повторов.** Недоставленное
  письмо просто теряется, запись об этом остаётся в журнале. Очередь с
  повторами имеет смысл добавить вместе с планировщиком.
- **Выгрузка отдаёт весь период целиком**, а не открытую страницу списка.
- **Итог в выгрузке заявок** — сумма показанных строк, включая отклонённые:
  это итог списка, а не обязательство компании.
