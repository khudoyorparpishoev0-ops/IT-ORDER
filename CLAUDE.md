# CLAUDE.md — HONA ORDER (заявки на расходы)

Внутренняя платформа IT-HONA: сотрудник подаёт заявку на расход, руководитель
согласует, финансы выплачивают. Суммы в сомони (TJS), интерфейс русский.

**Перед любой работой прочитай `docs/design/README.md`.** Это утверждённый
хендофф UI-кита (сентябрь 2026), он первичен для интерфейса; прототипы
рядом (`HONA ORDER - Приложение.dc.html`, `HONA ORDER - UI Kit.dc.html`,
скриншоты в `docs/screens/design/`). Старый хендофф `docs/DESIGN_HANDOFF.md`
оставлен как история. Брендбук `docs/Brand_Book_IT-HONA.pdf` приоритетнее
при расхождении. Этот файл — выжимка решений.

## Статус

- ✅ **Фаза 1 — каркас панели.** Vite + React 18 + TS, роутинг на 8 разделов
  и страницу-эталон `/system`, токены из брендбука, светлая и тёмная темы,
  два варианта шелла (B «Диспетчер» и C «Светлый»), модал заявки, тост,
  сортировка и фильтры таблиц, валидация комментария при отклонении.
- ✅ **Фаза 2 — бэкенд и реальные данные.** FastAPI + SQLAlchemy 2.0 (typed)
  + Alembic, 7 таблиц, жизненный цикл заявки с автоодобрением по порогу,
  отчёты (доли по объектам, факт по месяцам, реестр выплат, лимиты команды,
  бюджет), `/health` с состоянием базы и ревизией схемы. Панель ходит в API
  через `frontend/src/api/hooks.ts` (react-query); модуля с данными-примерами
  больше нет. 59 тестов pytest на настоящей PostgreSQL. Демо-набор —
  `python -m app.seed`.
- ✅ **Фаза 3 — вход и права.** Пароли Argon2id в `employees.password_hash`,
  сессия — JWT в httpOnly cookie (SameSite=Lax), матрица прав
  `app/core/permissions.py`, зависимость-страж `RequirePermission`.
  Сотрудник видит только свои заявки, руководитель согласует, финансы платят,
  администратор ведёт справочники и пароли. Панель: экран входа, скрытие
  разделов по правам, смена пароля, выход. Стартовый администратор из
  `BOOTSTRAP_ADMIN_*`. 119 тестов, из них 35 на разграничение прав.
- ✅ **Корпоративная почта и второй фактор.** Вход только с домена из
  `ALLOWED_EMAIL_DOMAINS`. TOTP (RFC 6238) с QR, кодами восстановления,
  защитой от повторного применения кода и блокировкой после серии неудач;
  обязателен ролям из `REQUIRE_2FA_ROLES`. Секрет в базе зашифрован
  ключом из `SECRET_KEY`.
- ✅ **Почта (Zoho).** SMTP через `app/core/mail.py`, шаблоны писем,
  восстановление пароля по ссылке, уведомление согласующим о новой заявке,
  проверочное письмо для администратора, живые переключатели уведомлений.
- ✅ **Путь через отдел закупа.** Сотрудник подаёт заявку без цен (что
  нужно, сколько, в чём) → руководитель согласует покупку → отдел закупа
  (роль `PROCUREMENT`, раздел «Закуп») проверяет склад и ставит цены →
  руководитель утверждает сумму → бухгалтерия платит. Что нашлось на
  складе, закрывается без денег; нашлось всё — заявка завершается статусом
  FULFILLED. Автоодобрения по сумме больше нет. Миграция `0006`.
- ✅ **Раздел «Объекты».** Справочник строек и площадок в панели (право
  `manage_reference`): завести, переименовать, отключить. В списке видно
  число заявок и расход по объекту — по ним понятно, что в работе и что
  можно закрывать. Удаления нет: объект живёт в заявках, а они неизменяемы.
- ✅ **Аудит и исправления (после жалобы «окно закрывается, сотрудник не
  заводится»).** Найдено и исправлено: модальное окно закрывалось от
  случайного клика мимо и от Escape, унося заполненную форму; истёкшая
  сессия молча подменяла экран на форму входа без объяснения; заведение
  сотрудника шло двумя запросами и при слабом пароле оставляло карточку
  без доступа; администратор мог сам одобрить и сам оплатить заявку, в том
  числе собственную; выплату принимали задним и будущим числом; `null` в
  обязательном поле давал 500; очередь согласования показывала только
  первые 50 заявок; сбой сервера выглядел как выход из системы.
- ✅ **Журнал действий.** Раздел «Журнал» (право `view_audit`, только
  администратор): кто входил и выходил, чьи попытки входа не прошли, кто
  что решил по заявкам и правил в справочниках. Фильтры по разделу,
  действию, сотруднику и датам, поиск, выгрузка в Excel. Пишется всё
  само: действующий сотрудник берётся из контекста запроса
  (`bind_audit_actor`), адрес — из middleware. Миграция `0005`.
- ✅ **Настоящий логотип.** В сайдбаре, на входе и на восстановлении пароля
  вместо набранного словами «IT-HONA» стоит фирменный логотип
  (`frontend/src/components/Logo.tsx`): три композиции — вертикальная
  (основная), горизонтальная (узкие места) и знак без слова (favicon).
  Геометрия из официальных файлов бренд-пакета, они же лежат в
  `docs/brand/` вместе с объяснением, почему панель не грузит их напрямую:
  имя там набрано SVG-шрифтом, а его не поддерживает ни один браузер.
- ✅ **Подача заявки и выплата в панели.** Кнопка «Новая заявка» открывает
  форму со строками сметы и итогом; «Сохранить черновиком» и «Отправить на
  согласование» — разные кнопки одной формы. Выплату финансы проводят в
  карточке одобренной заявки (способ + номер документа). До этого обе
  операции были доступны только через API, а кнопки в панели ничего не
  делали. Мёртвые кнопки без обработчика («Запросить уточнение»,
  «Подключить счёт», «Отправить в оплату») убраны или заменены рабочими:
  кнопка, которая молча ничего не делает, хуже отсутствующей.
- ✅ **Раздел «Сотрудники».** Экран управления справочником людей и их
  доступом: заведение с генерацией пароля, роль, замена
  пароля, сброс второго фактора, отключение уволенного, удаление записи без
  заявок. Виден только по праву `manage_reference`. До него сотрудников
  можно было завести лишь запросами к API.
- ✅ **Уведомления в Telegram.** Бот пишет автору заявки на каждом шаге
  (подана → согласована покупка → закуп проставил цены → сумма утверждена →
  оплачена/закрыта складом/отклонена) и зовёт того, к кому заявка пришла:
  руководителя, закуп, бухгалтерию. Привязка — через самого бота:
  «Параметры» → «Подключить Telegram» выдаёт одноразовую ссылку
  `https://t.me/<бот>?start=<код>`, id чата приходит от Telegram, когда
  человек нажимает «Старт». Отключение — кнопкой или командой `/stop`.
  Вебхук ставит администратор кнопкой в «Параметрах». Миграция `0008`.
- ✅ **Фаза 4 — планировщик.** Напоминание о заявках, которые стоят на одном
  шаге дольше `STALE_REQUEST_DAYS`, — тому, у кого заявка сейчас (по
  черновику — автору), одним списком в день в `REMINDER_HOUR`. По
  понедельникам — итоги недели тем, кто видит отчёты и включил сводку.
  Обе рассылки идут письмом и в Telegram. Тикер живёт в процессе `api`
  (`app/scheduler.py`), расписание — чистые функции
  (`app/services/schedule.py`), защита от повторов — уникальный `run_key`
  в `job_runs`. «Параметры» → «Фоновые задачи»: последние запуски и ручной
  прогон. Миграция `0009`.
- ✅ **Мобильная вёрстка.** Сайдбар на телефоне уходит из потока в шторку
  (раскладка переехала из инлайновых стилей в `shell.css`), сверху —
  полоса с логотипом и кнопкой меню, список заявок разворачивается
  карточками вместо таблицы, фильтры-чипы становятся лентой с прокруткой,
  строки сметы в форме идут в столбик. Проверяется `npm run mobile`.
- ✅ **Бюджет месяца из панели.** «Финансы» → «Задать бюджет»: сумму ставит
  бухгалтерия (право `pay_request`), руководитель её видит, но не меняет —
  это распоряжение деньгами, а не отчёт. Правка пишется в журнал вместе со
  старым значением: по нему видно, урезали бюджет или подняли. Сумма
  принимается как её пишут люди («150 000,00»). До этого бюджет заводился
  только запросом к API, то есть практически никем.
- ✅ **Фаза 5 — выгрузки.** Excel (openpyxl) и PDF (reportlab): реестр
  выплат, список заявок по фильтру, одна заявка для подшивки. Шрифты для
  PDF встроены в репозиторий и собираются `scripts/build_pdf_fonts.py`.
  Кнопки в панели работают, имя файла берётся из заголовка сервера.
- ✅ **Фаза 6 — развёртывание.** `docker-compose.prod.yml` с Caddy: HTTPS
  и продление сертификата автоматические, отдельный certbot не нужен.
  Панель слушает только `127.0.0.1`, наружу смотрит один Caddy.
  Скрипты `deploy/backup.sh` и `deploy/restore.sh`, процедура в README.

- ✅ **Установка на телефон (PWA).** Манифест, иконки из фирменного знака,
  service worker с офлайн-заглушкой, карточка «Приложение на телефоне» в
  «Параметрах» с кнопкой установки (Android) или подсказкой (iPhone).
  Ярлык «Новая заявка» → `/requests?new=1`. Воркер кэширует только
  `/assets/` и `/icons/`, API не трогает; версия подставляется при
  сборке, nginx отдаёт `sw.js` с `no-store`.

- ✅ **Push-уведомления на телефон (Web Push).** Ключ VAPID один
  (`VAPID_PRIVATE_KEY`, открытый выводится из него), генерируется
  `python -m app.push_setup`. Таблица `push_subscriptions` (миграция
  `0010`), сервис `app/services/push_notify.py` шлёт то же, что Telegram:
  автору — судьбу заявки, держателю — что заявка у него; напоминания и
  недельная сводка — в `reminders.py`. Мёртвые подписки (404/410 от
  push-службы) удаляются при отправке. Панель: карточка «Уведомления на
  телефоне» в «Параметрах», обработчики `push` и `notificationclick` в
  `sw.js`. Транспорт подменяется в тестах (`push_box`).

- ✅ **Черновик живёт в панели.** В карточке черновика — «Отправить на
  согласование», «Изменить» и «Удалить» (с подтверждением); правка идёт
  той же формой, что подача (`NewRequestModal` с `edit`). Заодно: в
  очереди согласования у неоценённых «не оценена» вместо «0,00», во
  вкладке «Сумма» один блок решения, действия закупа подписаны в
  журнале, справка переписана под нынешний путь заявки.

- ✅ **Редизайн по UI-киту (сентябрь 2026).** Панель переведена на новый
  дизайн: сайдбар forest с зелёным активным пунктом и счётчиком очереди,
  топбар 64 px с общим поиском и переключателем темы, статусы «рамка +
  точка», KPI-карточки, таблицы с шапкой zebra, workflow-лента этапов и
  блок «Сейчас ждёт» в карточке заявки. Карточка заявки — отдельная
  страница `/requests/:id` (решение, оценка закупа, выплата, действия по
  черновику — там же, модалки 440 px); форма — `/requests/new` и
  `/requests/:id/edit`. Согласование — список карточек с кнопками, Закуп —
  очередь таблицей. У заявки появилось наименование (`title` — первая
  позиция + «и ещё N») и общий поиск по номеру, объекту, автору и
  позициям. Вариантов шелла и плотностей больше нет — один каркас.
  Классы описаны в разделе «Конвенции → Фронтенд → UI-кит».
- ✅ **Логотип приложения ORDER.** Заказчик передал отдельный знак для

- ✅ **Помощник по материалам (Claude API).** Форма заявки по потере
  фокуса поля «Что нужно» зовёт `POST /api/materials/advice`; сервис
  `app/services/material_assistant.py` даёт модели каталог уже
  заказанного (`materials_catalog`) и просит грамотное написание,
  единицу и до двух подсказок (`messages.parse` по pydantic-схеме).
  Ответ — совет с кнопкой «Применить», не автозамена. Транспорт
  `app/core/assistant.py` подменяется в тестах (`assistant_box`),
  ключ `ANTHROPIC_API_KEY`, без него `GET /api/materials/assistant`
  отвечает `enabled=false`, и форма молчит. Ответы кэшируются в памяти.
- ✅ **Помощник по заявке (диалог).** Кнопка «Помощь AI» у позиций
  открывает `components/RequestAssistant.tsx`: сотрудник пишет как умеет,
  помощник задаёт до трёх вопросов с готовыми вариантами и возвращает
  позиции (`POST /api/assistant/request`). Сервис
  `app/services/request_assistant.py` кладёт в промпт контекст формы
  (сотрудник из сессии, объект, введённые строки) и каталог заказанного,
  историю диалога ведёт панель — на сервере состояния нет. Позиции
  переносит человек кнопкой «Применить в заявку»; заявка сама не
  отправляется. Правила — `app/services/assistant_prompt.py`, заменяются
  файлом через `ASSISTANT_PROMPT_FILE` без пересборки.
- ✅ **AI-аналитик для руководителя (ORDER Intelligence).** Раздел
  «Аналитика AI» под правом `view_reports`: сводка, заявки на внимание с
  причинами, этапы против нормативов, похожие заявки, объекты, люди,
  тренды недели и чат «Спросить ORDER AI». Считает всё
  `app/services/analytics.py`; `app/services/intelligence.py` отдаёт
  модели готовые факты текстом и получает объяснение по схеме. Роуты
  `GET /api/analytics/digest` (с `?ai=false` — только цифры, для
  карточки на дашборде) и `POST /api/analytics/ask`. Нормативы этапов —
  `SLA_*_HOURS` в `.env`, правила — `ANALYTICS_PROMPT_FILE`.
- ✅ **Хендофф UI-кита, вторая редакция (09.09.2026).** Два изменения:
  дашборд стал рабочей очередью, а на телефоне появилась нижняя панель

- ✅ **Журнал обращений к AI.** Каждое обращение к помощнику пишется в

## Принятые решения (не менять без согласования)

- **Дашборд — очередь, а не витрина.** Первый блок — то, что требует
  решения именно этого человека; собственные заявки в очередь не входят
  (их он решить не может, и кнопка была бы обманом). Порог задержки один
  для сервера и панели: `DELAY_DAYS = 3` в `services/requests.py` и в
  `data/status.ts`, менять парой.
- **Нижняя панель на телефоне — по требованию заказчика** (первый хендофф
  её запрещал): пять частых действий, полный список разделов остаётся в
  шторке по «Ещё». «Очередь» ведёт туда, где у роли лежат заявки
  (согласование / закуп / финансы), у сотрудника без очереди пункта нет.
  На форме заявки панели нет: это push-флоу со своими кнопками внизу.
  Содержимое получает `padding-bottom: 80px`, sticky-панель действий —
  `bottom: 64px`, иначе кнопки уходят под панель.
- **Один каркас панели.** Варианты шелла B/C и плотности убраны редизайном
  по UI-киту: сайдбар forest, топбар, одна плотность (строка 44 px).
  Тема — светлая и тёмная, переключатель в топбаре.
- **Дизайн-токены — единственный источник цвета и размера**
  (`frontend/src/styles/tokens.css`). Новых цветов и радиусов в компонентах не
  заводить. Радиусы только 0 / 2 / 4. Теней два уровня, третьего нет.
- **Шрифты из npm, самохостинг.** Manrope (основная), JetBrains Mono
  (служебный слой), Noto Sans (пара для таджикского). Подключаются только
  подмножества latin, latin-ext, cyrillic, cyrillic-ext — см.
  `frontend/src/styles/fonts.ts`. CDN запрещён: панель должна работать без
  интернета. Курсива нет, наклон не имитировать.
- **Статус всегда цвет и слово.** Точка 6 px плюс подпись в рамке цвета
  статуса (`StatusBadge`), цвет — из `frontend/src/data/status.ts`.
  Круглые аватары и «таблетки» запрещены; переключатели — прямоугольные
  `.toggle` 44×24 из UI-кита, чекбоксы квадратные.
- **Числа — ru-RU**: разделитель разрядов пробел, копейки запятая
  (`1 250 000,00`). Форматирование только через `frontend/src/data/format.ts`.
  Валюта указывается в заголовке столбца (`СУММА, TJS`) или словом «сомони»,
  знак валюты в число не ставится. Даты `00.00.0000`.
- **Один график — один вывод, он же заголовок.** Данные без источника и даты
  не публикуются. Круговые диаграммы не использовать, ось от нуля обязательна.
- **API вызывается с того же origin** через nginx-прокси, CORS не нужен.
- **История заявки только дописывается.** Ни API, ни панель не умеют
  править и удалять `request_events` — то же правило, что у `audit_log`.
  Запись, которую можно поправить задним числом, ничего не доказывает.
  Действующее лицо берётся из контекста запроса (`current_actor()`), а не
  из аргумента: имя от клиента подделывается, id вошедшего — нет. Имя всё
  равно хранится строкой: сотрудника переименуют или удалят, а история
  должна читаться и через год.
- **Просмотр — не событие ленты.** Карточку открывают по двадцать раз за
  день, и лента из просмотров вытеснила бы то, ради чего её открыли.
  Поэтому отдельная таблица с одной строкой на пару «заявка + сотрудник»
  и окном `VIEW_WINDOW` (30 минут): возвращения в его пределах — один
  просмотр, иначе счётчик показывал бы число обновлений страницы. IP и
  user-agent не собираются и не показываются: сотруднику они ничего не
  объясняют, а хранить их «на всякий случай» — это слежка за людьми, а не
  история заявки.
- **Решение человека и переход системы — разные события.** «Одобрил и
  передал» — это два дела, и одной строкой выходило, что маршрут выбрал
  руководитель. Он принял решение, маршрут выбрал ORDER. Системное
  событие подписывается «Система», `employee_id` и `actor_role` у него
  пустые: занять чужое имя под действие, которого человек не совершал,
  хуже, чем не назвать никого.
- **Персональных назначений нет и в истории.** Системный переход
  перечисляет тех, кто МОЖЕТ взять заявку (`details.waiting`), а не
  «ответственного»: закрепления людей за заявками в ORDER не существует,
  и выдумывать его в ленте значило бы обещать несуществующее.
- **Текст события — без рода.** «Оценка заявки», а не «Оценил»: пола
  сотрудника в ORDER нет и заводить его ради формулировки незачем, а
  «Ольга Кузнецова · Оценил» — опечатка, видная каждому. Имя и роль
  стоят строкой выше, и кто что сделал, понятно и так. То же правило,
  что с падежами: русский текст проверяется, а не собирается из кусков.
- **Роль в событии — снимок, а не ссылка.** Закупщика переведут в
  руководители, и «Оценка заявки · Руководитель» станет неправдой про
  уже случившееся. По той же причине имя хранится строкой.
- **Комментарий пишется до перехода, а не после.** Иначе в ленте выходит,
  что руководитель написал вслед уже ушедшей заявке, — а он написал,
  когда решал.
- **Порядок событий одной транзакции задаёт номер записи.** `now()` в
  PostgreSQL — время НАЧАЛА транзакции, поэтому у «одобрил» и «передала
  дальше» отметка совпадает до микросекунды. Отсюда `order_by` по паре
  (`created_at`, `id`) и такой же разбор ничьей в панели: без этого лента
  переставляет причину и следствие местами.
- **`details` события — данные, а не пересказ текста.** Панель рисует
  «было → стало» по ключам, а не разбирает `text` обратно: текст пишут
  для человека, и менять его должно быть безопасно. Ключ `amount` — всегда
  пара `{from, to}`, итоговая сумма шага идёт отдельным `amount_total`:
  одно имя для двух форм заставило бы панель гадать, что ей пришло. Пустая
  половина пары не рисуется вовсе — «Сумма →» не сообщает ничего.
- **Событие «изменено» бывает только у черновика.** После подачи заявка
  неизменяема, а сумму впервые проставляет закуп — и это отдельное
  событие. Правка без изменений в историю не пишется: «изменил» без
  изменений превращает ленту в шум и учит её не читать.
- **Форма заявки определяется категорией, и решает это сервер.** «Обед ·
  1 шт.» — не описание расхода, а попытка натянуть на него чужую форму.
  Категория задаёт и набор полей, и маршрут; прислать питание сметой
  строками нельзя даже прямым запросом к API. Панель рисует форму по
  ответу `GET /api/requests/categories` и своего списка полей не держит:
  разойдись форма с проверкой — и человек не сможет подать заявку, не
  понимая почему.
- **Реестр категорий — в коде, а не в таблице.** Его флаги решают, нужен
  ли отдел закупа и можно ли платить без второго согласования, то есть
  распоряжаются деньгами. Строка в базе, которую можно переключить мимо
  ревью, снимает закуп со всех материалов одним нажатием. Понадобится
  экран администратора — это отдельное решение владельца, а не побочный
  эффект удобства.
- **У заявки любого вида есть смета.** Для нестроковых категорий строку
  собирает сервер («Обед и ужин, 8 чел.-дн. по 50»): строки читают
  отчёты, аналитика, поиск, выгрузки, память помощника и наименование
  заявки — четырнадцать мест. Заявка без строк выпала бы из всех разом.
- **Выведенные строки — не материалы.** В подсказки к полю «что нужно»
  идут только заявки со сметой строками (`ai_memory._MATERIAL_CATEGORIES`):
  «Обед и ужин» никто не закажет повторно с автодополнения, а ленту
  частого такие строки забивают намертво.
- **Маршрут через закуп нужен там, где цену знает закуп.** Материалы,
  оборудование, хозрасходы и карго — через него. Питание, заправка,
  такси, проживание, связь с названной суммой идут от руководителя сразу
  в бухгалтерию: склад там не проверишь, счёт уже выставлен. Заявка без
  названной суммы идёт через закуп всегда — платить по нулю нельзя, и
  именно так описаны услуги.
- **Сумма считается на сервере и только `Decimal`.** Питание — человек ×
  дней × ставка, проживание — ночей × цена × комнат, командировка и карго
  складываются из статей. Панель показывает тот же итог, но справочно: в
  базу идёт серверный, и `amount` из тела запроса не берётся вовсе.
- **Заявка неизменяема после подачи.** Править состав можно только у
  черновика; решение и выплата происходят по одному разу. Ошибочное решение
  исправляется новой заявкой, а не правкой старой: иначе решение руководителя
  относилось бы к другому документу.
- **Номера заявок — из последовательности базы** (`request_number_seq`), а не
  из `max(number)`. Последовательность не откатывается, поэтому удалённый
  черновик не возвращает свой номер в оборот. Пропуски в нумерации допустимы,
  повторы — нет.
- **Деньги — только `Decimal` и `NUMERIC(12,2)`.** float для сумм запрещён.
  На фронтенд суммы приходят строками и форматируются как строки: перевод в
  `number` теряет копейки на больших значениях.
- **Статус меняется только в `app/services/requests.py`.** Роутеры и отчёты
  его не трогают.
- **Расходом считаются статусы PRICED, APPROVED, PAID** (`SPENT_STATUSES`):
  до оценки закупа суммы нет, отклонённая и закрытая складом заявка
  денег не стоила.
- **Лимитов на сотрудников нет.** Расход считается по объектам и по
  бюджету месяца; поле `monthly_limit` снято миграцией `0011`, в
  «Команде» — только расход и число заявок по людям. Заказчик: «у нас
  проекты, лимитов на людей не бывает».
- **Права — только в `app/core/permissions.py`.** Одна таблица ролей, а не
  проверки, разбросанные по роутерам: так видно всю картину и невозможно
  забыть закрыть новый эндпоинт. Неизвестная роль не получает ничего.
- **Разделение обязанностей:** кто согласовал — тот не платит; собственную
  заявку не согласуют даже с правом решения; заявку за другого подаёт только
  администратор.
- **Роль перечитывается из базы на каждом запросе**, а не берётся из токена:
  понижение прав должно действовать сразу, а не после истечения сессии.
- **Чужая заявка — 404, а не 403.** Иначе по коду ответа можно перебрать
  чужие номера. Фильтр по автору навязывает сервер (`_visible_employee_id`),
  клиентский параметр его не расширяет.
- **Имя действующего лица берётся из сессии**, а не из тела запроса: поле
  `actor` от клиента перезаписывается на сервере.
- **`/health` остаётся открытым** — его опрашивает Docker, плюс
  `/api/auth/policy` (показывает лишь допустимые домены почты). Всё
  остальное требует сессии.
- **Почта — логин и пропуск.** Нормализация и проверка домена только через
  `app/core/email_policy.py`; адреса хранятся в нижнем регистре, сравнение
  домена точное (не по вхождению, иначе `ithona.tj.evil.com` прошёл бы).
- **Домен почты не равен домену панели.** Панель — `order.ithona.tj`,
  корпоративная почта — `@ithona.tj` (`ALLOWED_EMAIL_DOMAINS`). Домен нигде
  не хардкодится: демо-данные и подсказки берут его из настроек, иначе
  демо-набор оказался бы бесполезен, а вход закрылся бы всем.
- **Домен почты в тестах закреплён** (`ALLOWED_EMAIL_DOMAINS=it-hona.tj`
  в conftest): смена домена заказчика не должна ломать прогон.
- **Токены различаются полем `typ`.** Промежуточный токен между факторами
  не должен открывать сессию — проверка обязательна в `token_subject`.
- **Незавершённый вход важнее действующей сессии.** Если в браузере остался
  чужой сеанс, настройка второго фактора относится к тому, кто входит
  сейчас (`_current_or_pending`), а начало нового входа гасит старую сессию.
- **Счётчик неудачных попыток коммитится отдельно.** Неудачный вход
  завершается исключением, и обработчик откатывает транзакцию — без
  явного коммита защиты от перебора не остаётся вовсе.
- **Коды восстановления удаляются запросом**, а не обходом
  `employee.recovery_codes`: коллекция в памяти бывает устаревшей, и старые
  коды переживали бы перевыпуск.
- **Письма уходят в фоне и не отменяют действие.** `send_quietly` для
  уведомлений, `send` — там, где вызывающий обязан увидеть ошибку
  (проверочное письмо администратора). Заявка должна быть подана, даже
  если SMTP недоступен.
- **Автоматическая сводка должна быть полезной, а не приходить.** Пустая
  вечерняя сводка не отправляется (`digest_when_no_changes`, по
  умолчанию false); «всё починилось» отдельным сообщением не шлётся
  вовсе — это число в вечерней сводке; один и тот же сигнал не
  повторяется чаще, чем раз в `CRITICAL_ALERT_REPEAT_HOURS`. Рассылка,
  приходящая каждые двадцать минут, за день приучает не открывать
  сообщения ORDER — и тогда пропущено будет и важное.
- **Аналитика отвечает «что произошло», рассылка — «кому, когда и
  куда».** `services/analytics/` не отправляет ничего и о Telegram не
  знает; `services/notifications/` не считает ничего и о SQL не знает.
  Второй набор расчётов «специально для рассылки» однажды разошёлся бы
  с первым, и цифра в утреннем сообщении перестала бы совпадать с
  цифрой на экране.
- **Время сводки — местное для каждого.** Пояс в `employees.timezone`,
  пусто — корпоративный `APP_TIMEZONE`. Общий час на всех означал бы,
  что кому-то сводка приходит ночью, а ночную сводку не читают — её
  отключают. Неизвестный пояс при отправке не отменяет сводку
  (подставляем корпоративный и пишем в лог), но при сохранении
  настройки отклоняется с ошибкой: человек должен увидеть опечатку
  сразу.
- **Право проверяется в момент отправки, а не при подписке.** Настройка
  правом доступа не является: роль могли понизить месяц назад. То же с
  отключённым сотрудником и отвязанным Telegram — доставку пропускаем,
  а настройку сохраняем: вернут на работу, и рассылка продолжится.
- **Защита от повторов у рассылки — та же, что у фоновых задач.**
  Уникальный `dedup_key` и вставка `ON CONFLICT DO NOTHING`: у сводки
  ключ «вид + человек + местная дата», у сигнала — «человек + заявка +
  причина», у сканирования — окно времени. Advisory lock здесь не
  подходит и в проекте не используется: он живёт в сессии и при падении
  воркера отпускается, а строка в таблице переживает и падение, и
  перезапуск. Строка появляется ДО отправки: пропущенная сводка — потеря
  на день, тройная — потеря доверия ко всей рассылке.
- **Сигнал — только про критичное.** Критично — это вдвое дольше
  норматива этапа (`stale.CRITICAL_FACTOR`). Обычная просрочка приходит
  утренней сводкой, и это правильное для неё место: сигнал на каждую
  задержку обесценивает сигналы.
- **Недоставленная сводка не переотправляется по кругу.** Ошибка
  Telegram пишется в историю доставок и видна администратору в
  «Параметрах»; ключ занят, и в этот день мы к человеку не вернёмся.
  Цикл переотправки при упавшем Telegram разбудил бы всех дважды, когда
  он поднимется. Сбой одного получателя не отменяет остальных и не
  роняет планировщик.
- **Молчание модели сводку не отменяет.** Цифры считает сервер, модель
  дописывает несколько строк словами. Нет ключа, кончились деньги,
  таймаут — уходит та же сводка без этих строк. Модели отдаётся не вся
  очередь, а первые `AI_CONTEXT_LIMIT` элементов: платить за сотни
  заявок в каждой утренней рассылке каждого руководителя незачем.
- **История доставок — не копия сообщения.** В `intelligence_deliveries`
  лежит, что и кому отправляли, сколько нашлось, звали ли модель и что
  ответил Telegram при отказе. Текста сводки там нет: он собирается из
  заявок, которые никуда не делись, а хранить вторую копию значит
  заводить второе место, где живут суммы и имена.
- **Планировщик — в процессе API, без отдельного контейнера и брокера.**
  Задач две, обе раз в сутки; celery или отдельный worker пришлось бы
  поднимать, обновлять и чинить ради этого. Раз в минуту тикер спрашивает
  у чистой функции, что пора, и занимает день уникальным `run_key` в
  `job_runs` — повтор невозможен ни при перезапуске, ни при двух
  процессах. Вставка идёт `ON CONFLICT DO NOTHING`: гонку решает база.
- **Пропущенный час не догоняется бесконечно.** Задача выполняется, если
  опоздание меньше `SCHEDULER_CATCH_UP_HOURS`, иначе день закрывается со
  статусом `SKIPPED`. Иначе поднятый ночью сервер разбудил бы людей
  напоминанием за вчера.
- **Напоминание идёт тому, у кого заявка стоит**, а не автору: автор своё
  уже сделал, а двигать заявку может только держатель. Своя заявка в
  напоминание не попадает — согласовать её человек всё равно не может.
  Одно письмо на человека со списком: пять писем подряд читают по
  диагонали.
- **У бота состояние на сервере, у панели — нет.** В вебе историю диалога
  присылает браузер, и сервер сессий не заводит. У Telegram браузера нет:
  между двумя сообщениями разговор держать больше негде, поэтому
  появилась `telegram_sessions`. Живёт сутки: заявка, которую начали
  вчера и бросили, сегодня уже про другое.
- **Заявку создаёт только `services/requests.py` — и из бота тоже.**
  Второго пути создания заявки в системе нет: иначе у него появятся свои
  правила, и однажды они разойдутся с панелью. Право `create_request`
  проверяется и в начале разговора, и у самой подачи: разговор мог
  начаться вчера, а роль с тех пор понизили.
- **Бот не отправляет заявку без подтверждения.** Последнее нажатие
  всегда за человеком — то же правило, что «Применить» в панели. Сбой
  помощника бота не закрывает: он записывает сказанное одной позицией и
  просит проверить количество.
- **Telegram привязывается через бота, а не вводом id.** Панель выдаёт
  одноразовый код (30 минут, одно применение), id чата приносит сам
  Telegram на `/start`. Спрашивать у человека номер или chat id незачем,
  а привязка чужого чата — это чужие уведомления о деньгах. Один чат
  принадлежит одному сотруднику: перепривязка к другому — 409, иначе
  первый тихо перестал бы получать сообщения.
- **Настройка бота доступна командой, а не только кнопкой:**
  `docker compose exec api python -m app.telegram_setup` (и `--check` для
  диагностики). Разбор «почему бот молчит» через панель требует до неё
  добраться, а собирать адрес вебхука в шелле из токена и `SECRET_KEY`
  руками — источник ошибок: одна такая команда с незаданной переменной
  затёрла токен в `.env` на боевом сервере.
- **Секрет вебхука выводится из `SECRET_KEY`** (`telegram_webhook_secret`),
  отдельной переменной нет. Это обычный `@property`, а не
  `computed_field`: вычисляемые поля попадают в `model_dump` и `repr`
  настроек, а секрету там не место. Смена `SECRET_KEY` или
  `PUBLIC_BASE_URL` требует нажать «Настроить бота на этот сервер» заново.
- **Push — как Telegram, только адресат другой.** Одно сообщение уходит
  во все каналы из одной точки (`_notify_telegram_later`), чтобы
  вызывающему не помнить про каждый. Endpoint подписки уникален: тот же
  браузер под другой учётной записью переводит подписку, а не дублирует —
  иначе чужие заявки приходили бы на чужой телефон. Ключ VAPID один:
  два ключа в `.env` — две возможности их перепутать. `pywebpush`
  закреплён на версии, совместимой с закреплённой `cryptography`.
- **Уведомление ведёт к карточке заявки**, а не в раздел:
  `request_url(request)` в `services/notifications.py` — одна точка для
  писем, Telegram и push. Со списка человеку ещё искать строку, а на
  телефоне ссылка открывается в браузере без сессии: после входа он
  должен оказаться у той заявки, к которой его позвали (экран входа
  рисуется на том же адресе, маршрут сохраняется). Списки напоминаний
  по-прежнему ведут в раздел — там заявок несколько.
- **Ответ помощника — это десятки секунд.** Таймаут клиента 90 секунд
  (`ASSISTANT_TIMEOUT_SECONDS`), у nginx для `/api/assistant/` — 300:
  при 20 секундах и минуте у nginx запрос обрывался, и панель честно
  писала «помощник недоступен», хотя ключ и деньги были на месте.
  Таймаут ловится отдельно от обрыва связи (`APITimeoutError` — наследник
  `APIConnectionError`, порядок except важен), причина отказа от Anthropic
  идёт в лог целиком. Разбор — `python -m app.assistant_check`.
- **Диалог помощника без состояния на сервере.** Историю реплик хранит
  панель и присылает в каждом запросе (не больше 12 последних): сервер
  не заводит сессий диалога, перезапуск `api` ничего не рвёт, а платить
  за пересылку всей переписки на длинных разговорах не приходится. Имя
  сотрудника берётся из сессии, а не из тела запроса.
- **Три написания позиции — три разные сущности.** `original_text` — что
  набрал человек; `normalized_text` — приведённое для поиска и сравнения;
  `title` — что в итоге вошло в заявку и что видят закуп и отчёты. Часто
  совпадают, но совпадение — частный случай. `title` исходным вводом НЕ
  является: «Применить» на совете помощника его переписывает, и набранное
  исчезло бы. Запоминает сырой ввод панель (`Line.original`) и присылает
  его при подаче; строка из шаблона, повтора или от помощника получает
  `original_text = title` — человек её не набирал, и выдумывать нечего.
  Разбор — `docs/ORDER_TEXT_FIELDS.md`.
- **Категория расхода — не справочник материалов.** Одиннадцать значений
  на всю компанию, меняются раз в годы; справочник материалов
  по-прежнему никто не ведёт. Поле необязательное: NULL значит «не
  указана», а не «Другое» — сваливать старые заявки в «Другое» значит
  испортить отчёт молча.
- **Модель не пишет SQL.** «Спросить ORDER AI» идёт в три шага: модель
  называет намерение из закрытого списка (`analytics/intents.py`), сервер
  выполняет соответствующую функцию, модель пересказывает результат.
  Данных в запросе на выбор намерения нет вовсе. Неизвестное имя — не
  ошибка: показываем общее состояние, модель пишет текст, а не код.
  Новая возможность аналитики — это новая функция в реестре, а не
  расширение свободы модели.
- **Нормативы этапов спрашивают у `analytics/sla.py`**, а не читают
  настройки по месту: «поменять SLA» должно означать одну правку, а не
  поиск трёх мест. Просрочка и застой — разные вещи: первая меряется
  нормативом этапа, вторая — временем без движения (`STALE_HOURS`).
  Заявка может укладываться в норматив и всё равно стоять сутки.
- **Отклонение — не нарушение.** Формулировка одна на весь раздел:
  «отличается от обычного уровня». Объект мог войти в активную фазу, а
  всплеск заявок означать, что стройка пошла. Сравниваем только с
  историей самой компании (неделя к неделе, месяц к месяцу): порогов «в
  абсолютных сомони» нет, у каждой компании свой масштаб. Рост с одной
  заявки до двух не показываем — это «плюс 100%» и ничего не значит.
- **Правило нестыковки должно быть узким.** Количество в описании
  сверяется с полем, только если число стоит в начале и за ним идёт
  счётное слово («2 мешка»). Широкое правило мы попробовали и выбросили:
  на демо-данных оно поймало четыре «нестыковки», и все четыре оказались
  выдумкой — «Шпатель 45 см» это размер, «Цемент М500» марка.
  Предупреждение, которое чаще неверно, чем верно, учит игнорировать все
  предупреждения подряд, включая настоящие.
- **Заявка попадает в очередь внимания один раз.** Две причины у одной
  заявки — это одно дело, а не два: иначе счётчик «требуют внимания»
  врёт в большую сторону, и очередь читается как катастрофа.
- **Ширина обзора аналитики считается из `view_all_requests`**, а не
  задаётся заново. У роли MANAGER это право уже есть: раздел «Заявки»,
  поиск и выгрузка и так показывают ей всю компанию. Сузить одну
  аналитику, оставив остальное, значит изобразить защиту, а не дать её —
  те же цифры человек соберёт руками за пять минут. Захочет заказчик
  сузить руководителя по-настоящему — менять надо матрицу прав, и тогда
  сузится всё разом.
- **Закрепления сотрудников за объектами в ORDER нет — и мы его не
  выдумываем.** Фальшивый scope опаснее честного широкого: он создаёт
  уверенность там, где её нет. Появится закрепление — сузится ровно
  `Scope.projects`, а вызывающие не изменятся; они уже получают `scope` и
  передают его в `stale.in_work`, единственную точку, где аналитика
  берёт заявки. Ограничение записано в `BLIND_SPOTS`. То же с отделами:
  `department_id` появится вместе с сущностью (`docs/DEPARTMENTS_PROPOSAL.md`).
- **Аналитика берёт заявки в одной точке** — `analytics/stale.in_work`.
  И сводка, и очередь внимания, и нестыковки идут отсюда, поэтому
  границу видимости достаточно навязать там: забыть её в одном из
  разделов невозможно.
- **Утреннюю сводку модель не помнит.** Сравнение «утро → вечер» считает
  сервер по сохранённым отметкам времени (`digest.overdue_delta`), а не
  память модели: она не источник истины. Сравниваются просрочки — у
  дубля и нестыковки нет времени, и «устранить» их за день нельзя.
- **Действующее лицо в вебхуке Telegram ставится руками** (`_bind`):
  зависимости `bind_audit_actor` там нет, вебхук открыт без входа. Без
  этой строки записи журнала из бота остаются безымянными, а оценить
  свой же ответ человек не может — обращение записано ни на кого.
- **Доступ к аналитике оставляет след.** Кто, какое намерение, сколько
  нашлось и звали ли модель (`analytics_view` / `ai_question`). Ни
  payload, ни ответ модели в журнал не пишем: он отвечает на вопрос «кто
  смотрел», а не хранит копию отчёта.
- **Аналитик не считает — считает сервер.** Все числа сводки и ответов
  приходят из `services/analytics.py`; модель получает их текстом и
  только объясняет. Иначе в сводке появлялись бы правдоподобные
  выдуманные цифры, а по ним распоряжаются деньгами. Номер заявки из
  ответа модели превращается в ссылку, только если он есть в фактах:
  выдуманный номер отбрасывается.
- **Аналитика закрыта правом `view_reports` целиком.** Обойти это
  вопросом невозможно: модель видит только подготовленный блок фактов,
  а не базу, и SQL не пишет. Вопросы пишутся в журнал (`analytics` /
  `ai_question`): доступ к данным всей компании должен оставлять след.
- **Про людей — только факты.** «Держит 14 заявок, 5 за нормативом» —
  да; «работает плохо» — нет. У задержки бывают причины, которых нет в
  данных: отпуск, объект без связи. Выводы делает руководитель.
- **Чего в ORDER нет, то не выдумывается.** Накладных и чеков файлами
  нет, отделов нет, приоритета и возврата на доработку нет. Это
  перечислено в `BLIND_SPOTS`, показывается в разделе и уходит в промпт,
  чтобы модель отвечала «таких данных нет», а не фантазировала.
- **Стоимость обращения — снимок, а не расчёт задним числом.**
  `cost_usd` пишется в момент обращения по тогдашней цене. Прайс
  Anthropic меняется, а расход за март не должен пересчитаться
  апрельской ценой: по этим цифрам сверяются со счётом. Записям старше
  миграции `0018` снимок задним числом НЕ проставлен — цена, по которой
  за них платили, неизвестна, и подставить сегодняшнюю значит выдать
  догадку за факт. Раздел считает их по нынешней таблице и помечает
  оценкой.
- **Цены моделей — одна таблица, подменяемая файлом.**
  `services/ai_pricing.py`, `AI_PRICES_FILE` для правки без пересборки:
  прайс меняется чаще, чем мы выкатываем релизы. В интерфейс цены не
  попадают вовсе — панель показывает готовую сумму, как и с сомони.
- **Незнакомая модель стоит «неизвестно», а не ноль.** Ноль означает
  «бесплатно», и расход выглядел бы меньше, чем он есть. Такая строка
  помечается в таблице моделей, а её сумма в расход не входит. Врать в
  меньшую сторону про деньги нельзя.
- **Отказ модели в разбивку по моделям не входит.** Ответа не получили,
  платить не за что; отказы видны отдельной долей. Иначе они выглядели
  бы безымянной моделью с неизвестной ценой.
- **Доля применённых делится только на те ответы, где кнопка была.**
  `applied = False` при создании там, где «Применить» есть, `NULL` там,
  где её нет (вопрос аналитику, сводка). До фазы 6 знаменателем были все
  ответы подряд, и доля выходила заниженной — метрика полезности врала в
  худшую сторону.
- **«Без модели» — только там, где обращение было.** Считаются алиас и
  кэш: ORDER ответил на заданный вопрос сам, бесплатно и мгновенно
  (`resolved_by`). Подсказки из памяти заявок, шаблоны и проверка
  повторов сюда не входят — это обычные запросы к базе, обращениями к
  помощнику они не были, и записывать их ради метрики значило бы завести
  второй журнал. Признак явный, а не выведенный из пустого `model`:
  пустая модель бывает и когда Anthropic ответил, но не отдал статистику.
- **Модель в журнале — та, что ответила.** Берётся из `response.model`, а
  не из настройки: в `.env` может стоять алиас, а Anthropic разворачивает
  его в конкретный снимок, и по счёту платят за снимок.
- **Расход обращений из планировщика считается отдельно**
  (`AiSource.SCHEDULER`). Ночная рассылка идёт каждый день сама; сложить
  её с обращениями людей — значит не понять, за что платим.
- **Бюджет AI предупреждает, но не выключает.** Порог
  (`AI_BUDGET_WARNING_PERCENT`) — повод человеку решить, а не системе
  отключить то, чем люди пользуются посреди рабочего дня. Автоотключения
  нет и не заводить без отдельного явного решения владельца. Бюджет
  считается по календарному месяцу: счёт Anthropic приходит за него же.
- **Стоимость — в долларах.** Счёт приходит в долларах; перевод в сомони
  по выдуманному курсу сверить со счётом было бы нечем. Понадобится
  курс — он задаётся вручную, а не тянется из внешнего источника.
- **Расход по сотрудникам — метрика использования, не рейтинг.**
  Помощник нужен тем, у кого много заявок, и частые обращения означают
  именно это. Список короткий (`EMPLOYEE_LIMIT`), выводов о работе
  людей раздел не делает — как и аналитика.
- **Журнал обращений — не память модели.** `ai_interactions` отвечает на
  вопрос «помогает помощник или мешает»: без доли применённых ответов
  это решается на глаз, а помощник стоит денег. Модели таблица не
  показывается никогда — память помощника это сами заявки. Ключа и
  секретов в записи нет; текст обрезается по `TEXT_LIMIT`, ответ из кэша
  пишется без времени (модель не ждали, и средняя задержка не должна
  выглядеть лучше, чем она есть). Номер записи возвращается панели, и по
  нему отмечается «Применить»; чужая запись не находится вовсе — как
  чужая заявка. Ключ в «Параметрах» показывается маской: начало и четыре
  последних знака, ровно чтобы отличить действующий ключ от старого.
- **Помощник советует, а не правит.** Написание материала меняется
  только кнопкой «Применить»: молчаливая автозамена подменила бы то,
  что человек просил, а отвечать за заявку ему. Сбой модели — не ошибка
  формы: `advise` не бросает, отдаёт `available=false`, подсказка не
  показывается. Модель зовётся по событию (поле потеряло фокус), не на
  каждую букву, и только для названий от трёх символов; одинаковые
  вопросы берутся из кэша. Каталог заказанного передаётся в промпт,
  чтобы модель предлагала принятое в компании написание, а не своё.
- **Сообщения бота уходят в фоне и не отменяют действие** — то же правило,
  что для писем: `send_quietly` в уведомлениях, ошибка только в лог.
- **У Zoho сервер зависит от региона** и нужен пароль приложения, а не
  пароль аккаунта — самые частые причины ошибки аутентификации.
- **Ссылка восстановления одноразовая** за счёт отпечатка пароля в токене:
  смена пароля гасит все выданные ссылки.
- **Восстановление пароля не выдаёт сессию** и не обходит второй фактор:
  доступа к почте недостаточно, чтобы войти.
- **Ответ на запрос восстановления одинаков** для известного и неизвестного
  адреса — иначе перебором выясняется, кто заведён.
- **Тесты не ходят в сеть:** автоиспользуемые фикстуры подменяют транспорт
  почты и Telegram. Без них прогон растягивался на минуты на таймаутах.
- **Коды восстановления показываются один раз.** Экран не переключать, пока
  человек их не подтвердил: в базе только отпечатки, повторно не покажет
  никто.
- **Выгрузка подчиняется тем же правам, что и экран.** Сотрудник получает
  файл только со своими заявками; ограничение навязывает сервер, а не
  параметр запроса.
- **В Excel суммы — числа с денежным форматом**, не строки: иначе получатель
  не просуммирует столбец. Гарнитура Arial — брендбук запрещает отдавать
  клиенту фирменные шрифты в офисных файлах.
- **Продукт называется ORDER, компания — IT-HONA LLC.** В документах и
  выгрузках «HONA ORDER» не пишется: это имя из ранних макетов. В коде
  `DOC_TITLE`, `COMPANY` и `SYSTEM_NAME` в `export_pdf.py`.
- **Текст из заявки попадает в PDF только через `_t()`.** `Paragraph` в
  reportlab разбирает мини-XML, и материал с названием «Уголок <30мм»
  ронял выгрузку в 500, а «Кабель <b>» подделывал вёрстку документа.
  Там же заменяются знаки, которых нет в шрифтах проекта: стрелку
  reportlab не рисует вовсе, и «Душанбе → Регар» печаталось как
  «Душанбе Регар» — маршрут терялся молча.
- **Шаг согласования в PDF — рубрика, а не фраза про человека.**
  «Нигина Рахимова · Провёл оплату» — опечатка, видная каждому, а пола
  сотрудника в ORDER нет. То же правило, что в истории на экране.
- **QR ведёт на обычный адрес заявки.** Ни токена, ни одноразовой
  ссылки: открывший его попадёт на экран входа и увидит заявку, только
  если имеет на неё право. Без `PUBLIC_BASE_URL` блока нет вовсе — код
  с «/requests/28» внутри телефон никуда не приведёт. Рисуется вектором
  по матрице: PNG на 300 dpi мылит края.
- **Шрифты PDF лежат в репозитории** (`app/assets/fonts`, SIL OFL). Пересборка
  — `scripts/build_pdf_fonts.py`; на сервере `node_modules` нет, а образ
  собирается без интернета. Manrope не содержит таджикских букв, их добирает
  Noto Sans — проверяется тестом на покрытие глифов.
- **Имя файла выгрузки кириллическое**, поэтому обязателен `filename*` по
  RFC 5987: обычный `filename` допускает только ASCII.
- **Именованные тома Docker не используем.** Всё персистентное — в папках
  хоста (`DB_DATA_PATH`). Кластер PostgreSQL во вложенной `pgdata/`.
- **Карта API наружу не отдаётся.** `/api/docs` и `/api/openapi.json`
  открыты только при `APP_ENV=development`. Данных они не раскрывают —
  каждый эндпоинт закрыт правом, — но выдают нападающему все адреса,
  параметры и схемы одним файлом и избавляют его от разведки, которую мы
  бы заметили по логам.
- **У каждого контейнера есть healthcheck.** Зависший nginx отвечает на
  TCP, но страницу не отдаёт, и без проверки Docker считает его живым.
- **Внешний ключ без индекса — это перебор таблицы.** Проверяется тестом
  по модели (`test_every_foreign_key_has_an_index`), а не глазами: индекс
  забывают ровно тогда, когда таблица ещё маленькая и разницы не видно.
  Колонка считается покрытой, только если она в индексе первая.
- **Секреты только в `.env`.** В логи не писать пароли и токены.
- **Скрипты не загружают `.env` в shell.** Файл написан для docker
  compose: значение с пробелом без кавычек (`MAIL_FROM_NAME=IT-HONA ORDER`)
  bash выполнил бы как команду `ORDER`. `deploy/backup.sh` и `restore.sh`
  читают нужные ключи через `env_value` (последний повтор побеждает, как
  в compose; кавычки и CR снимаются).
- **Новые значения `.env` применяются `docker compose up -d`**, не
  `restart`: перезапуск поднимает контейнер с прежним окружением.
- **Новая переменная `.env` — сразу строка в `docker-compose.yml`.**
  Контейнер `api` получает только перечисленные в `environment`
  переменные, `.env` целиком туда не передаётся. Ключ помощника
  пролежал в `.env` мёртвым грузом, пока его не добавили в compose.
  Заодно — в `OPTIONAL` скрипта `deploy/check-env.sh`.

## Факты об окружении

- **Сервер:** Ubuntu 22.04, Xeon 2×2.20 ГГц, 2 ГБ RAM, 30 ГБ SSD,
  IP 38.180.244.136 (Даллас). Публичный, а не LAN, поэтому вход и HTTPS
  обязательны до открытия доступа сотрудникам.
- **2 ГБ RAM** ограничивают: сборка фронтенда проходит, но тяжёлые сборки
  лучше делать в CI и переносить готовый образ.
- **Порты хоста:** 22, 80, 443. Панель (`WEB_PORT`, 8080) публикуется
  только на `127.0.0.1` — снаружи с ней говорит Caddy. API и база не
  публикуются вовсе.
- **HTTPS — Caddy, не nginx с certbot.** Выпуск и продление сертификата
  встроены, задание в cron не нужно. Папка `data/caddy` персистентна:
  её потеря означает повторный выпуск и риск упереться в лимиты
  Let's Encrypt.
- **`COOKIE_SECURE=true` в production.** По http браузер cookie не сохранит,
  поэтому HTTPS обязателен; для локальной разработки ставится false.
- **`SECRET_KEY` обязателен:** без него приложение не стартует в production,
  потому что любой смог бы подписать себе токен администратора.
- Репозиторий: `khudoyorparpishoev0-ops/IT-ORDER`.

- **Состояние доступа — отдельным эндпоинтом.** Список сотрудников
  (`GET /api/employees`) читает любой вошедший: без него не заполнить заявку.
  Кто когда входил, задан ли пароль, включён ли второй фактор — только
  `GET /api/employees/access` под правом `manage_reference`. Не добавлять эти
  поля в `EmployeeOut`: это раздаст их всей компании.
- **Последний администратор неприкосновенен.** `_keep_one_admin` в
  `app/services/reference.py` не даёт разжаловать, отключить или удалить
  единственную активную запись с ролью ADMIN — иначе справочники, роли и
  пароли не сможет менять никто, и доступ возвращается только правкой базы
  руками.
- **Смена пароля гасит все выданные сессии.** В токен кладётся отпечаток
  пароля (`pwd`), и сервер сверяет его на каждом запросе: сменили
  пароль — cookie, оставшаяся на чужом устройстве, перестала работать.
  Таблицы сессий в проекте нет и не нужно: она потребовала бы чистки,
  блокировок и своей истории, а тот же приём уже работал у ссылок
  восстановления. Токены, выданные до этой проверки, недействительны —
  после обновления все входят заново, один раз.
- **Пароль, выданный администратором, — временный.** Его знают двое, и
  заявка, поданная под ним, не доказывает, кто её подал. До смены сервер
  открывает ровно четыре адреса (`PASSWORD_CHANGE_ALLOWED` в
  `api/deps.py`): увидеть себя, сменить пароль, выйти, узнать политику
  входа. Список в одном месте, а не проверками по роутерам — забыть
  закрыть новый эндпоинт невозможно. Пароль, выбранный человеком самим
  (своя смена, ссылка из письма), временным не считается.
- **Сброс уволенному не делается.** Он не возвращает доступ, а открывает
  дверь обратно: сначала отметка «Работает в компании», потом пароль.
- **Неудачное подтверждение пишется в журнал** (`admin_password_reset_failed`).
  Попытка сбросить чужой пароль — то, о чём владелец должен узнать, даже
  если она не удалась. Ни кода, ни пароля в записи нет: только причина.
- **Работа с чужим доступом подтверждается кодом, а не сессией.** Смена
  чужого пароля и сброс чужого второго фактора — это захват учётной
  записи, в том числе бухгалтерии. Сессия администратора живёт часами:
  незакрытый ноутбук, украденная cookie, чужой человек за столом — и
  права у того, кто не вводил ни одного пароля. Поэтому спрашиваем то,
  чего вместе с сессией не украдёшь: код из приложения. Код
  восстановления тоже подходит — телефон теряют, а доступ нужен и в этот
  день. Без настроенного второго фактора действие не выполняется вовсе:
  иначе проверка обходилась бы простым «а у меня 2FA не включён».
  Неудачные попытки считаются общим счётчиком с входом: шестизначный код
  перебирается за миллион попыток, и открытая сессия администратора не
  должна становиться стендом для перебора.
- **Сброс второго фактора закрыт наравне со сменой пароля.** Закрыть
  только пароль значило бы не закрыть ничего: второй фактор сносится, и
  вход остаётся по одному паролю.
- **Пароль сотрудника показывается один раз.** Администратор генерирует его
  в карточке и передаёт лично; в базе только хэш Argon2. «Напомнить пароль»
  не делать — только выдать новый.

- **Журнал только дописывается.** Ни API, ни панель не умеют править и
  удалять записи `audit_log` — в этом весь смысл журнала. Чистки по сроку
  тоже нет: понадобится — делать отдельным заданием с явным решением
  владельца, а не молча.
- **Действующий сотрудник и адрес — из контекста запроса.** `write_audit`
  сам подставляет их (`app/core/audit_context.py`), поэтому в сигнатуры
  сервисов их тащить не нужно. Контекст задаётся ТОЛЬКО из асинхронного
  кода: async-зависимость `bind_audit_actor` на роутере и middleware с
  адресом. Синхронная зависимость выполняется в отдельном потоке с копией
  контекста, и запись из неё до обработчика не дойдёт.
- **Новый роутер с изменениями — с `dependencies=[Depends(bind_audit_actor)]`.**
  Иначе записи журнала останутся без имени.

- **Разделение обязанностей проверяется на запросе, а не только ролью.**
  Свою заявку нельзя ни согласовать, ни оплатить; кто одобрил — тот не
  платит. У администратора есть оба права, поэтому проверка именно на
  эндпоинте, а не в таблице прав.
- **Форма в модальном окне не закрывается молча.** `Overlay` с `dirty`
  спрашивает перед закрытием по клику мимо и по Escape (Escape нажимают,
  чтобы закрыть выпадающий список). Новая форма в окне — сразу с `dirty`.
- **401 в середине работы объясняется человеку.** `markSessionExpired()`
  из `api/session.ts` поднимает признак, экран входа показывает, что
  сессия истекла и введённое не сохранилось. Молча подменять экран нельзя:
  со стороны это выглядит как самопроизвольно закрывшееся окно.
- **Заведение с доступом — одним запросом.** Пароль передаётся в
  `POST /api/employees` вместе с карточкой и проверяется до создания.
  Двухшаговых сценариев, где половина сделана, а половина нет, не делать.

- **«У кого заявка» считается из статуса, а не хранится.** `awaiting_stage`
  и `awaiting_label` в `app/services/requests.py` — одна таблица переходов;
  время ожидания берётся от момента входа в текущий шаг
  (`sourcing_started_at`, `sourced_at`, `decided_at`), а не от подачи.
  Поимённый список ожидающих отдаётся только в карточке: в списке это был
  бы запрос на строку.
- **Контекст модели ограничен и собирается сервером.** Из пятисот прошлых
  заявок в промпт уходят десять самых относящихся к делу
  (`ai_memory.CONTEXT_LIMIT`), а не вся история. Дешевле, быстрее, короче
  по токенам и меньше поводов посоветовать не то. Насколько заявка
  относится к делу, считает `ranked()`: тот же сотрудник на том же
  объекте → тот же объект → тот же сотрудник → тот же материал →
  корпоративная частота, всё умножается на свежесть (вес падает вдвое за
  45 дней). Материал сравнивается вхождением в обе стороны, а не точным
  равенством: «гофра16» и «Гофра 16 мм» — одна вещь.
- **«Как в прошлый раз» ничего не создаёт.** Ни в панели, ни в боте:
  показываются найденные варианты с кнопками «Использовать», «Изменить»,
  «Другой вариант». Угадать можно и неверно, а деньги настоящие.
- **Заявка через Telegram — только от себя.** Просьбу подать «за
  Иванова» бот отклоняет фиксированной фразой и до модели не доводит:
  ответ один и тот же, а запрос стоит денег. В панели право подать за
  другого есть у администратора; в чате нельзя убедиться, кто пишет.
- **Приватность подсказок решается в одной точке**
  (`services/ai_privacy.py`). История всей компании используется, но
  только как знание о материалах: название, модель, характеристики,
  единица, факт частого использования, факт использования на объекте.
  Имя, суммы, комментарии и согласования — только по праву видеть чужие
  заявки. «UTP Cat6 Outdoor — часто на объекте Регар» можно всем;
  «Начиб заказывал его за 3 355 сомони» — никому без права.
- **Журнал обращений хранится 180 дней** (`AI_INTERACTIONS_RETENTION_DAYS`),
  чистит ночная задача `ai_retention`. Он вспомогательный: заявки, их
  текст, приведённое написание, `audit_log` и история статусов с ним не
  связаны ни ссылкой, ни каскадом и от чистки не зависят. Каскадом
  уходит только оценка ответа — мнение о несуществующем ответе не значит
  ничего. Основной журнал ORDER (`audit_log`) по-прежнему не чистится.
- **Шаблон принадлежит человеку, а не компании.** Общий список пришлось
  бы кому-то вести, а повторяющиеся дела у всех разные. Чужой шаблон —
  404, как чужая заявка. Применение подставляет состав, но заявку не
  подаёт. Отключённый объект шаблона не подставляется молча: ссылка
  снимается и человеку говорят выбрать другой.
- **Токены и модель пишутся в обращение**, если Anthropic их вернул
  (`assistant.last_usage()`). Без них стоимость ORDER AI известна только
  из счёта — задним числом и целиком, без разбивки по помощникам. Поля
  необязательные: SDK может не отдать статистику, и метрики это переживают.
- **Индексы, зависящие от расширений PostgreSQL, в модель не входят.**
  `pg_trgm` ставится миграцией, если база даёт права, а отказ
  перехватывается: поиск обязан работать и без него, через `ILIKE`.
  Такие индексы перечислены в `OPTIONAL_INDEXES` в `alembic/env.py`,
  иначе `alembic check` видит расхождение с моделью на пустом месте.
- **Память помощника — это база, а не модель.** Claude ничего не помнит
  между запросами и к PostgreSQL не подключается: выжимку по заявкам
  собирает сервер и отдаёт текстом, как в аналитике. Отсюда главное
  свойство: подсказки, «часто заказываете» и поиск повторов работают при
  выключенном помощнике — это обычные запросы к базе. Черновик в память
  не входит: его правят и удаляют, потребностью он ещё не стал.
- **Названия материалов общие, история — нет.** Что в компании называют
  «Кабель UTP Cat6», знать может каждый, иначе новый сотрудник не
  получит ни одной подсказки в первый день. А «кто, когда и на сколько
  заказывал» фильтруется тем же правилом, что список заявок: без
  `view_all_requests` человек видит только своё — и в «моём», и в
  повторах.
- **Алиас появляется от согласия человека, а не от модели.**
  `material_aliases` заполняется только нажатием «Применить»: поправку
  признали верной люди. Руками таблицу не ведут — это не справочник, а
  накопленное знание; справочник, который надо поддерживать, устареет за
  месяц. Известный алиас отвечает вместо модели: мгновенно, бесплатно и
  тем же ответом, что получил коллега.
- **Справочника материалов нет намеренно.** Подсказки для поля «что нужно»
  собираются из `expense_lines` (`materials_catalog`): отдельный справочник
  никто не станет вести, он устареет за месяц. Написания схлопываются по
  нижнему регистру, показывается вариант из самой свежей заявки.
- **Сумма заявки появляется только после закупа.** До этого `amount` —
  ноль, и показывать его числом нельзя: в списках и карточке стоит «не
  оценена». Признак `priced` в API отвечает именно на этот вопрос.
- **Складские строки денег не стоят.** `from_stock=true` — цена и итог
  NULL, в сумму заявки строка не входит, в отчётах не считается расходом.
- **Два решения руководителя — один эндпоинт.** `POST /decision` смотрит
  на статус: из PENDING одобрение отправляет в закуп, из PRICED — в оплату.
  Новых веток не заводить, иначе фронтенд начнёт угадывать, какую звать.
- **Свою заявку не оценивают.** Как согласование и выплата, оценка закупом
  собственной заявки запрещена на эндпоинте.

## Конвенции

**Бэкенд**

- Python 3.12, FastAPI, SQLAlchemy 2.0 (declarative, typed), Alembic,
  pydantic-settings (`app/config.py` — единственная точка чтения ENV).
- Слои: `app/schemas` (pydantic) → `app/services` (бизнес-логика, про HTTP не
  знает, поднимает `NotFoundError` / `ConflictError` / `ValidationError`) →
  `app/api` (роутеры). Ошибки превращаются в 404/409/422 в `app/api/errors.py`.
- Схема БД — только миграциями Alembic, `create_all()` в рантайме запрещён.
  Новая ревизия: `alembic revision --autogenerate -m "..." --rev-id 0002`.
  Перед коммитом: `alembic downgrade base && alembic upgrade head` и
  `alembic check`.
- Время — только через `app/core/time.py` (`utcnow`, `to_local`, `local_date`,
  `month_bounds`); naive datetime падает с ошибкой. В базе только
  `timestamptz` (UTC), бизнес-расчёты и отображение — `Asia/Dushanbe`.
- Деньги — только через `app/core/money.py` (`to_decimal`, `money`, `somoni`).
- В `app/api/deps.py` НЕ добавлять `from __future__ import annotations`:
  FastAPI не разворачивает отложенные аннотации в зависимостях-классах.
  В модулях с отложенными аннотациями у ответов 204 обязателен
  `response_model=None`, иначе FastAPI падает при старте.
- Любое изменение справочника или заявки пишет строку в `audit_log`
  (`write_audit`); имя, id сотрудника и адрес подставляются из контекста
  запроса. В `details` кладём человекочитаемое: имя сотрудника, название
  объекта — по журналу должно быть понятно, о ком речь, без похода в базу.
- Новое действие в журнале — сразу подпись в `app/core/audit_labels.py`
  И в `frontend/src/data/audit.ts`, иначе в панели будет голый код.
- Пароли и токены — только через `app/core/security.py`. Argon2 бросает
  `UnicodeEncodeError` на нелатинском мусоре в поле хэша, поэтому
  `verify_password` ловит его наравне с ошибками разбора: битая запись в базе
  не должна ронять вход.
- Маршрут с постоянным сегментом объявлять раньше маршрута с параметром:
  `/employees/access` после `/employees/{employee_id}` FastAPI разберёт как
  номер сотрудника и ответит 422.
- Новый эндпоинт закрывается правом сразу:
  `dependencies=[Depends(RequirePermission(Permission.X))]`. Открытым остаётся
  только `/health`.
- Настройки прогона фиксируются в `tests/conftest.py` (домен почты,
  `COOKIE_SECURE=false` — TestClient ходит по http и secure-cookie не хранит).
  Тесты не должны зависеть от `.env` на машине разработчика.
- Пустое значение в обязательном поле — 422 с понятным текстом, а не 500
  из глубины ORM. Проверять явный `null` в сервисе (`_REQUIRED_*_FIELDS`).
- Даты, приходящие от клиента (`paid_at`), проверять на будущее и на
  согласованность с историей: дата выплаты раньше решения или в будущем
  перекашивает все сводки, а исправить её потом нечем — история неизменяема.
- Путь заявки в тестах проводить фикстурами `advance` (сервисный слой) и
  `pipeline` (через API), а не повторять четыре шага в каждом тесте:
  процесс ещё будет меняться, и переписывать придётся одно место.
- Тесты pytest на критичную логику: переходы статусов, порог автоодобрения,
  суммы, лимиты, нумерация, форматы денег и времени. Работают на настоящей
  PostgreSQL — SQLite не воспроизводит NUMERIC, timestamptz и ограничения.
- Новая фоновая задача: обработчик в `app/services/jobs.py` (`HANDLERS` +
  `JOB_LABEL`), расписание — в `app/services/schedule.py`. Обработчик
  принимает `(session, *, now)` и возвращает строку для журнала запусков;
  падение обработчика не должно ронять цикл — это уже обеспечено.
- **Значения из `.env` обрезаются по краям** (`str_strip_whitespace` в
  `Settings`). Файл переносят на сервер через Windows, и он приезжает с
  CRLF: невидимый «\r» попадал в конец токена бота (Telegram отвечал
  «malformed URL») и пароля SMTP (отказ в логине при верном пароле).
  Симптомы у этого настолько косвенные, что дешевле срезать. То же ловит
  `deploy/check-env.sh` и подсказывает `sed -i 's/\r$//' .env`.
- Shell-скрипты в образах копируются отдельной строкой и чинятся от CRLF в том
  же слое: проект переносится через Windows, иначе контейнер падает с
  `env: bash\r: No such file or directory`.

**Фронтенд**

- **UI-кит — единственный источник вида.** Классы в `styles/base.css`,
  токены в `styles/tokens.css`, цвета только через `var(--token)`. Карта
  классов: `.card/.card-accent/.panel/.panel-head`, `.kpi-grid` + `Kpi`,
  `.btn` (`-primary/-secondary/-ghost/-danger/-icon/-sm/-dashed`), `.field`
  + `Field`, `.filter-row/.filter`, `.toggle/.toggle-row`, `.check/.check-row`,
  `.tbl` (`.cards` — карточки на телефоне, `.fit` — сжимается, `.compact`,
  `.tbl-forest`, `.tall`, `tr.clickable`, `tr.total-row`), `Pager`,
  `StatusBadge`, `Workflow`, `Waiting`, `.timeline/.tl-item/.tl-details`
  + `Timeline`, `.hbar/.vbars`, `Modal`,
  `ConfirmModal`, `.sticky-actions`, `.page-actions-desktop/-mobile`,
  `.desktop-only/.mobile-only`. Не путать `.stack` (колонка) и `.tbl.cards`.
- **Карточка заявки — страница, не окно.** Все действия по заявке живут в
  `pages/RequestPage.tsx`; списки только ведут туда. Новые действия
  добавлять там, а не в списках.
- **Наименование заявки считает сервер** (`title_of` в
  `services/requests.py`): первая позиция + «и ещё N». Отдельного поля
  названия нет и не будет.

- Service worker регистрируется только в production-сборке
  (`import.meta.env.PROD`) и только после `load`. Данные API в нём не
  кэшировать. `beforeinstallprompt` перехватывается в `src/pwa.ts` до
  монтирования React, иначе кнопка установки останется без события.
  Снимок состояния для `useSyncExternalStore` кэшируется: новый объект
  на каждый вызов — бесконечный перерендер.

- Страницы в `frontend/src/pages`, общие компоненты в `frontend/src/components`,
  шелл в `frontend/src/shell`, работа с API в `frontend/src/api`.
- Запросы к бэкенду только через хуки `src/api/hooks.ts` (react-query).
  Типы `src/api/types.ts` зеркалят pydantic-схемы — при изменении схемы на
  бэкенде обновлять их здесь же.
- Текущий пользователь и права — через `useAuth()` из `src/api/auth.tsx`.
  Скрытие разделов по правам — только удобство: решение принимает сервер.
- 401 обрабатывается один раз в `main.tsx` (QueryCache/MutationCache), а не
  в каждом компоненте: сессия может истечь между любыми двумя запросами.
- Запрос, закрытый для роли, не отправлять вовсе (`enabled` у useQuery):
  иначе панель стучится в закрытый эндпоинт и получает 403.
- Загрузку, ошибку и пустоту рисует `QueryState`, а не каждая страница по-своему.
- **Раздел, которого нет в справке, для сотрудника не существует.** Он
  его не найдёт и не откроет, сколько ни строй. Поэтому новая
  возможность в панели — это новый вопрос в `pages/Help.tsx`, наравне с
  README и `.env.example`. Группы вопросов скрываются по правам: учить
  сотрудника пользоваться «Журналом» значит отправлять его искать пункт
  меню, которого он не увидит.
- **Диагностика не ругается на исправную систему.** `check-env.sh`
  проверяет `BOOTSTRAP_ADMIN_*` отдельным блоком «Первый запуск»: пустые
  они — норма, потому что README велит их удалить после первого входа.
  Скрипт, который выдаёт замечание всегда, перестают читать целиком —
  вместе с теми замечаниями, ради которых он написан.
- Пустой список в форме объяснять по причине, а не одной фразой на все
  случаи: «не загрузилось», «всё отключено» и «ничего не заведено» лечатся
  по-разному, а одинаковая подсказка отправляет человека искать не туда.
- Справочник, от которого зависит форма, перезапрашивать при её открытии
  (`refetchOnMount: 'always'`): вкладка у сотрудника открыта с утра, а
  объект администратор завёл минуту назад.
- Логотип — только `IthonaLogoStacked` / `IthonaLogo` / `IthonaMark` из
  `components/Logo.tsx`. Набирать имя шрифтом нельзя: начертание фирменное,
  и в вебе его нет — в компоненте буквы разложены в контуры. Цвет — один,
  через `color`: на светлом `var(--logo)` (зелёный), на тёмном и на зелёном
  белый — так требует бренд-бук. Композиции и отступы не менять.
- Модальные окна — `components/Overlay.tsx` (Escape, клик мимо, единственная
  разрешённая тень), поля — `components/Field.tsx`. Не копировать разметку
  окна в страницу.
- Подпись поля связывать с полем через `htmlFor`/`id`, а не обёрткой `<label>`
  вокруг всего блока: иначе в доступное имя поля попадают пояснение и соседние
  кнопки, диктор читает мешанину, а `getByLabel` в дымовом прогоне находит не
  то поле («Пароль» содержит «роль»).
- Суммы приходят строками и форматируются `money()` из `src/data/format.ts`
  без перевода в `number`.
- Русский текст проверять на падежи: после «за» — винительный
  («за сентябрь»), имена людей в предлоги не ставить (они требуют склонения,
  которое мы не делаем) — давать через двоеточие. Числительные склонять:
  `plural()` во фронтенде, `app/core/text.py` на сервере — «2 выплаты», а
  не «2 выплат».
- Скачивание — через `useDownload()`: обычная ссылка не покажет отказ по
  правам, браузер просто откроет вкладку с JSON. Blob освобождать с
  задержкой, немедленный `revokeObjectURL` срывает загрузку.
- Проверка перед коммитом: `npm run build` (tsc + vite) и `npm run smoke`
  (все разделы в обеих темах, ошибки консоли и 4xx/5xx).
- Фокус единый: `outline: 2px solid var(--green)` с отступом 2 px, без
  смещения элемента. Все интерактивные элементы достижимы Tab, Esc закрывает
  модал.
- Кнопки 44 px (48 px на мобильных), строка таблицы 44 px, контент до 1240 px.
- **Раскладку задавать классами, а не инлайновым `style`.** Инлайн сильнее
  медиазапроса: `position: sticky` в атрибуте сайдбара пережил
  `position: fixed` из `shell.css`, и на телефоне колонка продолжала
  занимать 256 px, уводя всю страницу вбок. Инлайн — только для того, что
  зависит от данных или выбранного варианта оформления (цвета шелла).
- **Всё, что лежит в grid- или flex-контейнере, должно уметь сжиматься:**
  минимальный размер по умолчанию равен содержимому, поэтому широкая
  таблица внутри карточки распирает колонку. У `.card` стоит
  `min-width: 0`, у вложенных flex-блоков с длинным текстом — тоже;
  прокрутку широкой таблицы берёт на себя `.table-wrap`.
- **Минимальная ширина таблицы — через `--tbl-min`,** а не инлайновым
  `min-width`: на телефоне медиазапрос снимает её (`.tbl.fit`) или
  разворачивает строки карточками (`.tbl.stack`, список заявок).
- Проверка вёрстки на телефоне — `npm run mobile`: скрипт падает, если
  страница, шторка меню или модальное окно прокручиваются вбок.
- Анимация одна: 150 ms ease-out. Параллакс, появление блоков по скроллу,
  переходы между экранами и градиенты запрещены.
- Комментарии и текст интерфейса — на русском, идентификаторы кода — на
  английском. Эмодзи в интерфейсе запрещены.
- Чтение localStorage оборачивать в try/catch: в приватном окне доступ бросает
  исключение, приложение не должно падать.

## Правила работы

1. Работать по фазам, маленькими шагами. Проект целиком не переписывать.
2. После каждой фазы: `pytest`, `npm run build` и `npm run smoke` должны
   проходить, README обновляться (таблица фаз), `.env.example` дополняться.
3. Чего-то не хватает от заказчика (логотип, реальные данные, роли) —
   остановиться и спросить, не выдумывать.
4. Дизайн воссоздаём библиотечными компонентами проекта. Рантайм прототипа
   (`docs/prototype_expense_platform.dc.html`) в продукт не тащить — оттуда
   берём структуру экранов, размеры, копирайт и поведение.
